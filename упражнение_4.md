# Архитектура SuperSurance — Упражнение 4: Межсервисный join

> Строится поверх схемы Упражнения 3.

## 1. Контекст

После разделения на домены данные лежат в физически разных БД, и простой join средствами БД невозможен. Пример из задания: сотруднику нужна таблица всех запросов на расчёт с клиентом, данными ТС и страховым продуктом.

Где эти данные сейчас:

| Данные | Сервис | БД |
|---|---|---|
| Запросы на расчёт, статус, премия | Proposal | Proposal DB (`proposals`, `proposal_details`) |
| ТС | Proposal | Proposal DB (`vehicles`) |
| Клиент | Customer | Customer DB (`clients`) |
| Продукт, тариф | Product | Product DB (`products`, `tariffs`, `tariff_versions`) |
| Задача андеррайтинга | Underwriting | Underwriting DB (`tasks`) |

Требования: db-links запрещены; нужны фильтрация, сортировка и пагинация.

## 2. Решение: CQRS read model (витрина)

Вводим **Query Service** с собственной **Read DB**, в которой хранится заранее соединённая (денормализованная) витрина. Витрина наполняется доменными событиями из брокера, введённого в Упражнении 3. Back-office получает списки из Query Service, а не из доменных сервисов.

### 2.1. Query Service + Read DB
- Подписан на события Customer, Product, Proposal, Underwriting.
- Хранит **локальные реплики** нужных полей (`clients_replica`, `products_replica`) и **денормализованную таблицу** `proposal_list_view`.
- Join выполняется внутри одной Read DB, поэтому фильтрация, сортировка и пагинация — обычные средства СУБД с индексами.
- Только чтение: ничего не меняет в доменных сервисах.

**Витрина `proposal_list_view`:**

| Группа | Поля |
|---|---|
| Заявка | proposal_id, status, calc_type (auto / manual), premium, created_at, updated_at |
| Клиент | client_id, client_full_name, client_birth_date |
| ТС | vehicle_id, vin, make, model, year |
| Продукт | product_id, product_name, tariff_version_id |
| Андеррайтинг | task_status, assignee_id |

Индексы — под реальные фильтры экрана: статус + дата, product_id, VIN, ФИО (поиск по префиксу).

### 2.2. События, которые наполняют витрину

| Событие | Публикует | Что обновляет |
|---|---|---|
| `ClientCreated`, `ClientUpdated` | Customer | `clients_replica` + ФИО во всех строках клиента |
| `ProductCreated`, `ProductUpdated` | Product | `products_replica` + название продукта |
| `ProposalChanged` (новое) | Proposal | Строка витрины; событие несёт все поля заявки для витрины: статус, тип расчёта, премию, даты, client_id, данные ТС, product_id, `tariff_version_id` |
| `UnderwritingTaskCreated`, `UnderwritingTaskClaimed` (новое), `UnderwritingTaskReleased` (новое), `UnderwritingCompleted` | Underwriting | task_status, assignee_id |

`ProposalChanged` публикуется при любом изменении предложения и несёт его состояние целиком (event-carried state transfer). События из Упражнения 3 (`UnderwritingRequested`, `ProposalCalculationFailed`) остаются: это сигналы для конкретных потребителей, а `ProposalChanged` — источник данных для витрины.

**Реплики** `clients_replica` и `products_replica` нужны, потому что событие о заявке несёт только `client_id` и `product_id`: ФИО и название продукта берутся из локальной реплики, без синхронного запроса в Customer или Product.

Следствие для схемы: **Customer и Product получают outbox** и начинают публиковать события, а Proposal и Underwriting публикуют новые события.

### 2.3. Какие данные — «на момент расчёта», а какие — текущие
- **Тариф** — на момент расчёта: событие Proposal несёт `tariff_version_id`, поэтому изменение тарифа не переписывает историю расчётов.
- **ФИО клиента, название продукта** — текущие значения: при `ClientUpdated` / `ProductUpdated` обновляются все строки.
- **ТС** — из события Proposal (данные ТС по-прежнему живут в Proposal).

Это бизнес-решение; на защите стоит проговорить его явно.

### 2.4. Надёжность наполнения
- Публикация — Transactional Outbox в каждом сервисе-источнике.
- Идемпотентность — учёт обработанных `event_id`, повтор события не дублирует строку.
- Порядок — события одной заявки обрабатываются по порядку: ключ сообщения = `proposal_id`, в том числе для событий задач андеррайтинга.
- События из разных сервисов могут прийти в любом порядке, поэтому обновления делаются как upsert: если строки заявки ещё нет, она создаётся с заполненными полями задачи, а остальные поля заполнятся при `ProposalChanged`.

### 2.5. API списков
`GET /api/query/proposals?status=PENDING_UNDERWRITING&product_id=...&vin=...&client_name=Иван&created_from=...&created_to=...&sort=created_at,desc&limit=50&cursor=...`

- **Фильтрация** — по любым полям витрины.
- **Сортировка** — по индексированным полям.
- **Пагинация** — keyset (cursor), чтобы не деградировать на глубоких страницах. Общее количество — отдельный запрос или оценка.

Доступ — через Internal Gateway, роли `admin` и `underwriter`.

### 2.6. Детальный экран
Карточка одной заявки собирается в BFF через **API Composition** (Proposal + Customer + Product по id): по одной записи это дёшево и всегда даёт актуальные данные. Витрина — только для списков.

## 3. Согласованность

Витрина согласована в конечном счёте (eventual consistency): задержка — секунды.
- В UI показывается «данные на ЧЧ:ММ».
- После собственного действия пользователя (например, андеррайтер установил премию) карточка читается из исходного сервиса, а не из витрины.

## 4. Почему не другие варианты

| Вариант | Почему нет |
|---|---|
| db-links | Запрещено стандартами компании |
| API Composition для списков | Нельзя сортировать и пагинировать по полям из разных сервисов без выгрузки всех данных |
| Общая БД для отчётов с прямым чтением чужих таблиц | Ломает Database per Service из Упражнения 2 |
| CDC (Debezium) по таблицам сервисов | Витрина завязывается на внутренние схемы БД сервисов, нужна вторая инфраструктура рядом с брокером |
| Копировать чужие данные в Proposal | Proposal становится владельцем чужих данных и разрастается |

## 5. Изменения на схеме относительно Упражнения 3

- Новый **Query Service** и **Read DB** (отдельная группа «Read side»).
- Связь Internal Gateway → Query Service (списки).
- Query Service подписан на брокер.
- Customer и Product публикуют события в брокер (outbox в их БД).
- Proposal публикует `ProposalChanged`, Underwriting — `UnderwritingTaskClaimed` и `UnderwritingTaskReleased`.

## 6. Допущения

- ТС остаются в Proposal, как в Упражнениях 2–3. Если ТС переедут в отдельный домен, в витрину добавится ещё один источник событий; подход не меняется.
- В витрине есть персональные данные клиентов, поэтому доступ к Query Service ограничивается ролями; детальная модель доступа — Упражнение 5.
- Стек не фиксируем: Read DB — реляционная СУБД; при необходимости полнотекстового поиска — поисковый движок.
