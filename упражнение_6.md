# Архитектура SuperSurance — Упражнение 6: Паттерны

> Строится поверх схемы Упражнения 5. Архитектура не менялась: на схему добавлены только цветные бейджи с кодами паттернов и «Каталог паттернов» внизу.

## 1. Как читать схему

Код на бейдже = **буква уровня + номер паттерна**. Бейдж стоит на нижней границе компонента, где паттерн применяется. Паттерны, относящиеся ко всей группе компонентов (микросервисы, Database per Service, Event-Driven), показаны в правом верхнем углу группы «Сервисы» и на брокере.

| Буква | Уровень | Цвет | Что это |
|---|---|---|---|
| **A** | Архитектурные | фиолетовый | как система разбита на части и как части связаны |
| **I** | Интеграционные и обмен сообщениями | оранжевый | как компоненты обмениваются данными (REST, события, команды) |
| **D** | Данные | бирюзовый | как данные хранятся, копируются, кэшируются, версионируются |
| **R** | Надёжность и эксплуатация | красный | как система переживает сбои и как за ней наблюдают |
| **S** | Безопасность | синий | аутентификация, доступ, защита данных |
| **P** | Проектирования | серый | паттерны внутри компонента (в духе GoF) |

Цвета компонентов (новый / изменён) остались как в Упражнении 5: в этом упражнении ничего нового не добавлялось.

## 2. Архитектурные паттерны (A)

| Код | Паттерн | Где на схеме | Какую проблему решает |
|---|---|---|---|
| A1 | **Микросервисы + Bounded Context (DDD)** | группа «Сервисы» | Монолит разделён по бизнес-областям (клиенты, продукты, заявки, андеррайтинг, портфель, уведомления). Команды развивают свой домен независимо |
| A2 | **Database per Service** | группа «Сервисы», все БД | У каждого сервиса своя БД, другие сервисы не читают её напрямую. Отсюда проблема join из Упр. 4 |
| A3 | **Event-Driven Architecture, Pub/Sub, хореография** | брокер | Сервисы реагируют на события друг друга без прямых вызовов; новые потребители подключаются без изменения издателя |
| A4 | **CQRS** | Query Service, Read DB | Чтение (списки с фильтрами) отделено от записи (доменные сервисы) |
| A5 | **API Gateway** | API Gateway | Единая точка входа для сайта, мобильного приложения и партнёров: маршрутизация, ограничение частоты, проверка токенов |
| A6 | **Backend for Frontend (BFF)** | Internal Gateway | Отдельный вход для сотрудников: свои роли, WebSocket, сборка карточек |
| A7 | **Saga / Process Manager (оркестрация)** | Workflow Orchestrator | Долгий процесс «Выпуск предложения» из нескольких шагов в разных сервисах, с таймерами и повторами |

Хореография (A3) и оркестрация (A7) используются вместе сознательно: простые реакции остаются хореографией, оркестрация — только там, где процесс длиннее двух шагов и нужна видимость «где завис».

## 3. Интеграционные паттерны и обмен сообщениями (I)

| Код | Паттерн | Где на схеме | Зачем |
|---|---|---|---|
| I1 | **Transactional Outbox** | Customer DB, Product DB, Proposal DB, Underwriting DB, Notification DB, Reference DB | Событие записывается в ту же транзакцию, что и бизнес-данные; нет ситуации «данные сохранили, событие потеряли» |
| I2 | **Idempotent Consumer** | Query, Orchestrator, Notification, Document Service | Повторная доставка события не создаёт дубль (учёт `event_id`, ключи дедупликации) |
| I3 | **Event-Carried State Transfer** | Proposal Service | `ProposalChanged` несёт состояние заявки целиком, потребителю не нужно обращаться за данными к издателю |
| I4 | **Порядок по ключу (партиционирование)** | брокер | События одной заявки идут по порядку: ключ сообщения = `proposal_id` |
| I5 | **Retry topics + Dead Letter Channel** | Retry / DLQ | Сбойное сообщение не блокирует очередь: повторы, затем DLQ, оттуда replay |
| I6 | **Schema Registry (контракт событий)** | Schema Registry | Формат события нельзя сломать незаметно для потребителей: проверка совместимости схем |
| I7 | **API Composition** | Internal Gateway | Карточка заявки собирается из Proposal, Customer, Product по id; для одной записи это дёшево и актуально |
| I8 | **Anti-Corruption Layer** | Integration Service | Модель данных партнёров не просачивается в нашу: перевод форматов и кодов (в т.ч. код партнёра ↔ код НСИ) |
| I9 | **Async Request-Reply (202 Accepted)** | API Gateway | Если расчёт нельзя выполнить сразу (например, задача андеррайтеру), клиент получает 202 и узнаёт результат позже |
| I10 | **Work Queue + claim (Competing Consumers)** | Underwriting Service | Очередь задач; андеррайтер забирает задачу (claim), её не берёт другой |
| I11 | **Server Push (WebSocket)** | Notification Service → Internal Gateway | Сотрудники получают уведомления о задачах и ошибках без опроса |

## 4. Паттерны данных (D)

| Код | Паттерн | Где на схеме | Зачем |
|---|---|---|---|
| D1 | **Materialized View (реплики в Read DB)** | Read DB | Заранее соединённая витрина `proposal_list_view` и реплики клиентов и продуктов: join внутри одной БД |
| D2 | **Cache-Aside** | Redis | Повторный платный запрос к партнёру не делается: сначала кэш, при промахе запрос и сохранение |
| D3 | **Инвалидация кэша событием + stale-if-error** | НСИ | Справочники кэшируются в потребителях, сбрасываются событием `ReferenceDataChanged`; при недоступности НСИ работаем на последнем кэше |
| D4 | **Keyset (seek) pagination** | Query Service | Страницы не замедляются на большой глубине |
| D5 | **Eventual Consistency + upsert** | Read DB | События из разных сервисов приходят в любом порядке; строка витрины создаётся и дополняется по мере прихода |
| D6 | **Idempotency Key + версия агрегата** | Proposal, Document Service | Документ и процесс привязаны к `proposal_id + version`: повтор не создаёт второй документ |
| D7 | **Versioned Reference / Snapshot** | Product Service, Document DB | Тариф фиксируется на момент расчёта (`tariff_version_id`), данные документа сохраняются снимком |
| D8 | **Append-only журнал / WORM** | Audit DB, Object Storage | Записи аудита и готовые документы нельзя изменить задним числом |
| D9 | **Reference Data Management (MDM)** | НСИ | Один источник правды для общих справочников вместо копий в каждом сервисе |

## 5. Надёжность и эксплуатация (R)

| Код | Паттерн | Где на схеме | Зачем |
|---|---|---|---|
| R1 | **Retry with backoff** | Integration Service, Workflow Orchestrator | Временные сбои партнёров и шагов процесса переживаются повторами с нарастающей паузой |
| R2 | **Circuit Breaker** | Integration Service, Channel Gateway | Если партнёр или провайдер недоступен, не тратим на него запросы и не вешаем расчёт |
| R3 | **Failover / Fallback** | Channel Gateway | Второй SMS / e-mail провайдер; резервный канал (e-mail → SMS) |
| R4 | **Rate Limiting** | API Gateway | Защита от перегрузки и злоупотреблений на входе |
| R5 | **Observability: трассировка, correlation id, логи** | блок «Сквозные средства» | Сквозной `correlation_id` через gateway, сервисы и события; алерты по lag, DLQ, ошибкам партнёров |

## 6. Безопасность (S)

| Код | Паттерн | Где на схеме | Зачем |
|---|---|---|---|
| S1 | **Federated Identity / SSO, токены (JWT)** | IAM | Единый вход и токены вместо паролей в каждом сервисе |
| S2 | **RBAC + атрибутный доступ (ABAC)** | IAM | Права по ролям; ограничение по атрибутам (партнёр видит только свои заявки) |
| S3 | **Gateway Offloading** | API Gateway, Internal Gateway | Проверка токена, срока и грубых прав вынесена на границу, а не повторяется в каждом сервисе |
| S4 | **Defense in Depth** | группа «Сервисы» | Сервисы проверяют права сами: обход gateway не открывает данные |
| S5 | **Valet Key (pre-signed URL)** | Object Storage | Клиент скачивает документ по короткой ссылке напрямую из хранилища, без прокси через сервисы |
| S6 | **External Secrets Store** | Secrets & Config | Ключи партнёров, провайдеров и пароли БД лежат в Vault, а не в коде и конфигах |
| S7 | **Audit Log** | Audit Service | Неизменяемый журнал, кто и что делал, включая доступ к ПДн |
| S8 | **Шифрование + маскирование данных** | Защита данных | Шифрование ПДн и документов, маскирование в логах и для ролей без права `pii:read` |
| S9 | **Service-to-service auth** | IAM, Защита данных | Сервисы получают короткоживущие токены (client credentials) и общаются по mTLS |

## 7. Паттерны проектирования внутри компонентов (P)

Эти паттерны не видны на уровне компонентной схемы, это решения внутри сервисов. Бейджи показывают, в каком компоненте они применяются. Часть из них — рекомендованная реализация, а не факт, зафиксированный в упражнениях, поэтому колонка «Статус» их отмечает.

| Код | Паттерн | Где | Зачем | Статус |
|---|---|---|---|---|
| P1 | **Adapter** | Integration Service, Channel Gateway | Адаптер на каждого партнёра и провайдера приводит их API к единому внутреннему контракту; замена партнёра не затрагивает остальной код | следует из ACL и Channel Gateway |
| P2 | **Strategy** | Proposal Service | Правила расчёта премии и правило «в андеррайтинг» подключаются как взаимозаменяемые правила, а не зашиваются в код | рекомендация |
| P3 | **Caching Proxy** | Redis перед Integration Service | Вызывающий код не знает, ответ пришёл из кэша или от партнёра | следует из Cache-Aside |
| P4 | **State (статусы и переходы)** | Proposal, Underwriting, Orchestrator | Статусы заявки и задачи, допустимые переходы и события на переходах описаны явным автоматом | рекомендация |

## 8. Что сознательно не используется

| Паттерн | Почему нет |
|---|---|
| **Event Sourcing** | Достаточно outbox и обычных таблиц. Хранить историю изменений как источник истины нужды нет, аудит и документы закрывают потребность в истории |
| **Распределённые транзакции (2PC)** | Заменены Saga, Outbox и идемпотентными потребителями |
| **Общая БД / db-links** | Запрещены стандартами и ломают Database per Service |
| **Service Mesh / Sidecar** | mTLS предусмотрен, но способ реализации (mesh или библиотеки) в упражнениях не фиксировался |
| **Strangler Fig** | Применим как способ миграции из монолита (Упр. 2), но на целевой схеме не виден |

## 9. Что стоит добавить при реализации

Это замечания по результатам анализа, на схему они не вынесены.

- **Bulkhead** для Integration Service: отдельные пулы соединений на каждого партнёра, чтобы медленный партнёр не занимал ресурсы остальных.
- **Явные таймауты** на все синхронные вызовы (Proposal → Integration, Document Service → Proposal). Сейчас таймаут заложен только как параметр шага оркестратора.
- **Inbox** (таблица обработанных `event_id`) для идемпотентных потребителей, явно описанная в каждом потребителе.
- **Health checks** и readiness-пробы для всех сервисов, чтобы оркестратор контейнеров не направлял трафик на неготовый сервис.
- **Feature flags** в централизованной конфигурации для безопасного включения новых правил расчёта.

## 10. Допущения

- Паттерны перечислены те, что следуют из принятых решений Упражнений 1–5. Если паттерн возникает как следствие нескольких решений, он отмечен на каждом компоненте, где проявляется.
- Паттерны уровня P (проектирование) частично рекомендательные: детали реализации внутри сервисов упражнениями не задавались.
- Названия паттернов взяты из общепринятых каталогов (Enterprise Integration Patterns, Microservices Patterns, паттерны облачного проектирования, GoF).
