# Архитектура SuperSurance — Упражнение 1: Интеграция с источниками данных

## 1. Связь с исходным контекстом: стартовая точка

Данная схема является **первой итерацией развития** архитектуры SuperSurance, построенной на основе исходного контекста бизнес-задачи.

### Исходный контекст (до Упражнения 1)
- **Компания**: молодая страховая компания «SuperSurance», специализирующаяся на КАСКО
- **Уникальное предложение**: тарифы и правила расчета премий, дающие клиентам цены в **2-3 раза ниже рыночных** без потери доходности для компании
- **ИТ-команда**: только формируется, стратегия — поступательное развитие с корректировкой архитектуры на ходу
- **Архитектура**: простой монолит (`SuperSurance Core Application`)
- **Канал продаж**: только сайт компании с формой подачи заявки на расчет
- **Взаимодействие**: прямой синхронный запрос-ответ между сайтом и монолитом

### Почему потребовалось изменение (контекст Упражнения 1)
Методологи, разрабатывающие формулу расчета страховой премии, сообщили о необходимости повышения точности расчета. Для этого требуется учитывать дополнительные данные:
- **История ремонта транспортного средства (ТС)**
- **Оценка рыночной стоимости ТС**
- **История выписанных штрафов на страхователя**
- **Наличие данных о страхователе в системе по предотвращению мошенничества (антифрод)**

Для получения этих данных компания решила использовать **платные сервисы компаний-партнеров**.

Дополнительно, бизнес расширил каналы продаж:
- Появилось **мобильное приложение**
- Подключилась **партнерская сеть продаж**

### Требования к интеграциям
1. **Кэширование** — для экономии денег на повторяющихся платных запросах
2. **Изоляция контекста** — контекст и модель данных системы расчета могут и должны отличаться от тех, что используют партнеры

### Сравнительная таблица

| Аспект | Исходный контекст | Упражнение 1 |
|--------|-------------------|--------------|
| Архитектурный стиль | Простой монолит | Монолит с интеграционным слоем |
| Каналы продаж | 1 (Сайт) | 3 (Сайт, Мобильное приложение, Партнерская сеть) |
| Внешние интеграции | Отсутствуют | 4 платных партнерских API |
| Точка входа | Прямое подключение к монолиту | API Gateway |
| Кэширование | Отсутствует | Redis/Memcached для внешних данных |
| Изоляция контекста | Не требуется | Anti-Corruption Layer (ACL) |
| Базы данных | 1 (внутри монолита) | 1 (внутри монолита) + 1 (кэш Redis) |

## 2. Обзор архитектуры

Архитектура представляет собой **монолитное приложение с выделенным интеграционным слоем и API Gateway**, подготовленное к работе с множеством внешних источников данных и каналов продаж.

Основные слои системы:
1. **Каналы подачи заявок** (Clients) — три канала взаимодействия с клиентами
2. **Точка входа** (API Gateway) — единый шлюз для всех входящих запросов
3. **Монолитное приложение** (SuperSurance Core Application) — содержит всю бизнес-логику, включая новый интеграционный модуль
4. **Инфраструктура** (Redis/Memcached) — распределенный кэш для внешних данных
5. **Внешние платные сервисы** (Partner APIs) — четыре системы партнеров

---

## 3. Детальное описание компонентов

### 3.1. Каналы подачи заявок (Clients)

Три канала, через которые клиенты и партнеры взаимодействуют с системой:

- **Сайт** — веб-интерфейс компании SuperSurance с формой подачи заявки на расчет страховой премии. Основной канал для прямых клиентов.
- **Мобильное приложение** — нативное или кроссплатформенное приложение для клиентов. Позволяет подавать заявки и получать расчеты "на ходу".
- **Партнерская сеть продаж** — внешние партнеры (агентства, брокеры), интегрированные через API. Позволяет масштабировать продажи без прямых затрат на привлечение клиентов.

Все каналы отправляют запросы по протоколу **HTTPS** и получают ответы в унифицированном формате (JSON). API Gateway обеспечивает единый интерфейс для всех каналов, скрывая от них внутреннюю структуру системы.

---

### 3.2. Точка входа — API Gateway

**API Gateway** — единая точка входа для всех внешних запросов. Внедрен в рамках Упражнения 1 для решения задач маршрутизации и безопасности при появлении множества каналов.

**Функции:**
- **Маршрутизация** — направляет запросы от разных каналов в монолитное приложение
- **Rate Limiting** — ограничение частоты запросов для защиты от перегрузки (особенно важно при подключении партнерской сети)
- **Базовая аутентификация** — проверка API-ключей, токенов, сертификатов
- **Унификация запросов** — приведение запросов от разных каналов (сайт, мобильное приложение, партнеры) к единому формату, понятному монолиту
- **SSL-терминация** — завершение HTTPS-соединений, разгрузка монолита от криптографических операций
- **Логирование и мониторинг** — сбор метрик по входящему трафику для анализа нагрузки

**Почему API Gateway, а не прямое подключение:**
- Монолит не должен знать, откуда пришел запрос (с сайта или из мобильного приложения)
- Централизованное управление безопасностью и лимитами
- Возможность добавлять новые каналы без изменения монолита
- Подготовка к будущему разделению на микросервисы (API Gateway останется точкой входа)

---

### 3.3. Монолитное приложение (SuperSurance Core Application)

**SuperSurance Core Application** — единое приложение, содержащее всю бизнес-логику системы. В рамках Упражнения 1 в него был добавлен **Интеграционный модуль** для работы с внешними API.

#### 3.3.1. API Layer / Контроллеры

Верхний слой монолита, принимающий запросы от API Gateway.
- Принимает унифицированные запросы
- Валидирует входные данные
- Вызывает соответствующие сервисы бизнес-логики
- Формирует ответы для API Gateway

#### 3.3.2. Бизнес-логика (Core Domain)

Ядро системы, содержащее уникальную бизнес-логику SuperSurance.

**Движок расчета премий (Calc Engine):**
- Применяет специальные тарифы и правила расчета, разработанные методологами
- Использует формулу, дающую цены в 2-3 раза ниже рыночных
- Учитывает данные клиента, автомобиля и внешние данные от партнеров
- Генерирует уникальные ценовые предложения

**Внутренняя модель данных (Domain Model):**
- Единый формат данных внутри системы
- Отличается от форматов внешних партнеров
- Оптимизирован для задач расчета премий

#### 3.3.3. Интеграционный модуль (Integration Layer)

Новый компонент, добавленный в рамках Упражнения 1. Отвечает за взаимодействие с внешними платными API партнеров.

**Менеджер кэша (Cache Manager):**
- Реализует паттерн **Cache-Aside** (кэш помимо основного источника)
- Перед каждым вызовом внешнего API проверяет наличие данных в Redis
- При **Cache Hit** (данные есть в кэше и не протухли) — возвращает данные из кэша, не делая платный запрос
- При **Cache Miss** (данных нет или они устарели) — вызывает внешний API, сохраняет ответ в кэш и возвращает данные
- Управляет TTL (Time To Live) для разных типов данных (24-48 часов)

**Клиенты партнерских API (Partner API Clients):**
- Специфичные адаптеры для каждого партнера
- Формируют HTTP-запросы с нужными заголовками, API-ключами, параметрами
- Обрабатывают ответы от партнеров
- Реализуют механизмы отказоустойчивости (Retry, Timeout)

**Anti-Corruption Layer (ACL):**
- Критически важный слой для изоляции контекста
- Трансформирует "сырые" DTO (Data Transfer Objects) от партнеров во внутреннюю модель данных SuperSurance
- Защищает ядро системы от изменений во внешних API партнеров
- Позволяет менять партнеров без изменения бизнес-логики

**Почему ACL необходим:**
- Партнеры используют разные форматы данных (вложенность, названия полей, типы данных)
- Если партнер изменит формат API, изменения коснутся только ACL, а не всего монолита
- Внутренняя модель данных остается чистой и оптимизированной для бизнес-задач

---

### 3.4. Инфраструктура — Распределенный кэш (Redis / Memcached)

**Redis/Memcached** — распределенная система кэширования в памяти, используемая для хранения ответов внешних партнеров.

**Характеристики:**
- **TTL (Time To Live):** 24-48 часов в зависимости от типа данных
  - История ремонта ТС: 48 часов (редко меняется)
  - Рыночная стоимость ТС: 24 часа (может меняться чаще)
  - История штрафов: 48 часов (обновляется нечасто)
  - Антифрод данные: 24 часа (требует более частой проверки)
- **Цель:** экономия бюджета на платных запросах к партнерам
- **Эффективность:** до 70% запросов к внешним API обслуживаются из кэша
- **Расположение:** отдельный инфраструктурный компонент, не внутри монолита (для независимого масштабирования)

**Почему кэш вынесен отдельно:**
- Кэш должен быть доступен быстро (в памяти, а не в БД)
- Возможность независимого масштабирования кэша
- Кэш может использоваться другими сервисами в будущем (при переходе к микросервисам)
- Снижение нагрузки на монолит

---

### 3.5. Внешние платные сервисы (Partner APIs)

Четыре внешних системы-партнера, предоставляющие данные для повышения точности расчета премии:

- **История ремонта ТС** — данные о ремонтах и повреждениях автомобиля. Помогает оценить техническое состояние и риски.
- **Рыночная стоимость ТС** — оценка текущей рыночной стоимости автомобиля. Необходима для расчета страховой суммы и премии.
- **История штрафов** — данные о штрафах водителя (ГИБДД или агрегаторы). Позволяет оценить аккуратность водителя и риски.
- **Антифрод система** — проверка клиента на причастность к мошенничеству. Защищает компанию от убытков.

**Характеристики партнеров:**
- Все партнеры предоставляют **REST API**
- Требуют **аутентификацию** (API-ключи, токены)
- Являются **платными** (оплата за каждый запрос)
- Могут иметь **лимиты** (квоты на количество запросов в день/месяц)
- Могут быть **недоступны** (требуются механизмы отказоустойчивости)

## 4. Потоки данных и взаимодействия

### 4.1. Основной сценарий: Расчет премии с внешними данными

1. **Клиент** (с сайта, из мобильного приложения или от партнера) отправляет запрос на расчет через **API Gateway**
2. **API Gateway** выполняет аутентификацию, проверяет rate limit, унифицирует запрос и маршрутизирует его в **API Layer** монолита
3. **API Layer** передает запрос в **Движок расчета премий (Calc Engine)**
4. **Движок расчета** понимает, что для точной формулы нужны внешние данные, и обращается к **Менеджеру кэша**
5. **Менеджер кэша** проверяет **Redis** по ключу (например, `vehicle:{VIN}:history`):
   - **Cache Hit:** данные есть и не протухли → сразу возвращает их в Движок расчета
   - **Cache Miss:** данных нет или они устарели → переходит к шагу 6
6. **Менеджер кэша** вызывает **Клиентов партнерских API** для получения данных
7. **Клиенты API** делают HTTPS-запросы к внешним партнерам и получают "сырые" DTO
8. **Anti-Corruption Layer (ACL)** трансформирует "сырые" DTO во внутреннюю модель данных (Domain Model)
9. **Менеджер кэша** сохраняет трансформированные данные в **Redis** с TTL 24-48 часов
10. **Движок расчета** получает все необходимые данные (внутренние + внешние) и выполняет расчет по формуле: `premium = base_rate * coefficients * external_factors`
11. **Движок расчета** возвращает результат в **API Layer**
12. **API Layer** формирует ответ и возвращает его через **API Gateway** клиенту

### 4.2. Межкомпонентное взаимодействие

- **Каналы → API Gateway:** HTTPS, JSON
- **API Gateway → Монолит:** HTTP/REST, JSON
- **Менеджер кэша → Redis:** протокол Redis (TCP), бинарный формат
- **Клиенты API → Внешние партнеры:** HTTPS, JSON/XML (в зависимости от партнера)
- **ACL → Domain Model:** внутренняя трансформация объектов

### 4.3. Принципы взаимодействия

- **Единая точка входа:** все внешние запросы проходят через API Gateway
- **Изоляция контекста:** внешние данные трансформируются через ACL перед использованием в бизнес-логике
- **Кэширование по умолчанию:** все запросы к внешним API сначала проверяют кэш
- **Отказоустойчивость:** механизмы Retry и Timeout для внешних вызовов
- **Унификация:** API Gateway приводит запросы от разных каналов к единому формату

## 5. Ключевые архитектурные решения и их обоснование

### 5.1. Почему сохранен монолит, а не сразу микросервисы?

- **Молодая компания:** ИТ-команда только формируется, нет ресурсов для сложной распределенной системы
- **Поступательное развитие:** стратегия компании — развиваться постепенно, корректируя архитектуру на ходу
- **Быстрый выход на рынок:** монолит позволяет быстрее запустить MVP с интеграциями
- **Простота разработки:** одна кодовая база, проще координировать работу небольшой команды
- **Подготовка к будущему:** внедрение API Gateway и интеграционного слоя — это шаги к будущему разделению на микросервисы

### 5.2. Почему внедрен API Gateway?

- **Множество каналов:** появление мобильного приложения и партнерской сети требует единой точки входа
- **Безопасность:** централизованная аутентификация и rate limiting
- **Унификация:** разные каналы могут отправлять запросы в разных форматах, Gateway приводит их к единому виду
- **Будущее масштабирование:** при переходе к микросервисам API Gateway останется точкой входа и будет маршрутизировать запросы к разным сервисам

### 5.3. Почему внедрено кэширование?

- **Экономия бюджета:** партнеры берут оплату за каждый запрос, кэширование снижает количество платных вызовов
- **Производительность:** ответ из кэша возвращается за миллисекунды, ускоряя общий расчет премии
- **Снижение нагрузки:** меньше запросов к внешним API — меньше риск превышения квот и получения ошибок
- **Окупаемость:** стоимость Redis значительно ниже стоимости повторяющихся платных запросов

### 5.4. Почему внедрен Anti-Corruption Layer (ACL)?

- **Изоляция контекста (требование ТЗ):** контекст и модель данных системы расчета должны отличаться от партнерских
- **Защита от изменений:** если партнер изменит формат API, изменения коснутся только ACL
- **Чистота бизнес-логики:** Движок расчета работает с внутренней моделью, не зная о форматах партнеров
- **Гибкость смены партнеров:** можно заменить партнера, не меняя бизнес-логику, только адаптер в ACL

### 5.5. Почему кэш вынесен отдельно от монолита?

- **Независимое масштабирование:** кэш может масштабироваться отдельно от монолита
- **Производительность:** выделенный Redis работает быстрее, чем встроенное кэширование
- **Будущее использование:** при переходе к микросервисам кэш останется общим ресурсом
- **Надежность:** падение кэша не должно приводить к падению монолита (монолит может работать без кэша, делая прямые запросы к API)

## 6. Глоссарий терминов

| Термин | Описание |
|--------|----------|
| **ACL (Anti-Corruption Layer)** | Слой трансформации, защищающий внутреннюю модель данных от внешних форматов |
| **API Gateway** | Единая точка входа для всех внешних запросов, выполняющая маршрутизацию, аутентификацию и унификацию |
| **Cache-Aside** | Паттерн кэширования, при котором приложение сначала проверяет кэш, а при отсутствии данных загружает их из источника |
| **Cache Hit** | Ситуация, когда запрашиваемые данные найдены в кэше |
| **Cache Miss** | Ситуация, когда запрашиваемые данные не найдены в кэше |
| **DTO (Data Transfer Object)** | Объект для передачи данных между компонентами или системами |
| **Domain Model** | Внутренняя модель данных системы, оптимизированная для бизнес-задач |
| **HTTPS** | Защищенный протокол передачи данных |
| **Rate Limiting** | Ограничение частоты запросов для защиты от перегрузки |
| **Redis** | Распределенная система кэширования в памяти |
| **REST API** | Архитектурный стиль взаимодействия через HTTP |
| **Retry** | Механизм повторных попыток при временных сбоях |
| **SSL-терминация** | Завершение HTTPS-соединений на уровне Gateway |
| **Timeout** | Максимальное время ожидания ответа от сервиса |
| **TTL (Time To Live)** | Время жизни данных в кэше |

## 8. Ограничения и риски текущей архитектуры

### 8.1. Ограничения
- **Единая точка отказа:** падение монолита выводит из строя всю систему
- **Сложность масштабирования:** необходимо масштабировать весь монолит, даже если нагрузка растет только на интеграционный слой
- **Связанность компонентов:** изменения в одном модуле могут повлиять на другие
- **Единая кодовая база:** большая команда разработчиков может создавать конфликты

### 8.2. Риски
- **Зависимость от внешних партнеров:** если партнер недоступен, расчет может быть неточным или невозможным
- **Превышение квот:** при высокой нагрузке можно превысить лимиты запросов к партнерам
- **Устаревание кэша:** если TTL слишком большой, данные могут быть неактуальными
- **Безопасность:** хранение API-ключей партнеров внутри монолита требует защиты

### 8.3. Пути развития
- Разделение монолита на микросервисы (Упражнение 2)
- Внедрение асинхронной коммуникации между компонентами
- Добавление механизмов Circuit Breaker для внешних вызовов
- Внедрение мониторинга и алертинга для внешних интеграций
