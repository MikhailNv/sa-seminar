# Архитектура SuperSurance — Упражнение 2: Сегментация на домены

## 1. Связь с Упражнением 1: эволюция архитектуры

Данная схема является прямым развитием и усовершенствованием архитектуры, полученной по итогам **Упражнения 1**.

### Что было в Упражнении 1
- **Монолитная архитектура**: единое приложение `SuperSurance Core Application`, содержащее всю бизнес-логику, интеграционный слой, кэширование и работу с данными.
- **API Gateway** как единая точка входа для трех каналов (Сайт, Мобильное приложение, Партнерская сеть).
- **Интеграционный модуль** с Anti-Corruption Layer (ACL) и кэшированием (Redis) внутри монолита.
- **Единая БД** для хранения всех данных системы.

### Почему потребовалось изменение (контекст Упражнения 2)
Компания SuperSurance начала расти, появились специализированные бизнес-команды, каждая из которых отвечает за свою предметную область:
- Управление клиентами и клиентской базой
- Управление продуктами и тарифами
- Сопровождение выданных предложений
- Мониторинг портфеля застрахованных ТС
- Управление партнерской сетью

Руководство приняло решение **распределить ИТ-систему по этим командам**, предоставив каждой возможность развивать свой домен **самостоятельно и изолированно**. Это потребовало сегментации монолита на доменные сервисы с собственными базами данных.

### Сравнительная таблица

| Аспект | Упражнение 1 | Упражнение 2 |
|--------|--------------|--------------|
| Архитектурный стиль | Монолит | Микросервисы (доменные сервисы) |
| Количество сервисов | 1 (Core Application) | 5 (4 доменных + 1 интеграционный) |
| Базы данных | 1 общая | 4 отдельных (Database per Service) |
| Команды разработки | 1 общая | 4+ специализированных |
| Развертывание | Единое | Независимое для каждого сервиса |
| Масштабирование | Вертикальное (весь монолит) | Горизонтальное (по сервисам) |

## 2. Обзор архитектуры

Архитектура представляет собой **доменно-ориентированную микросервисную систему** (Domain-Driven Microservices), состоящую из следующих основных слоев:

1. **Каналы подачи заявок** (Clients) — точки взаимодействия с внешним миром
2. **Точка входа** (API Gateway) — единый шлюз для всех входящих запросов
3. **Доменные сервисы** (Domain Services) — бизнес-логика, разделенная по предметным областям
4. **Домен интеграций** (Integration Domain) — централизованное взаимодействие с внешними системами
5. **Внешние платные сервисы** (Partner APIs) — системы партнеров-поставщиков данных

---

## 3. Детальное описание компонентов

### 3.1. Каналы подачи заявок (Clients)

Три канала, через которые клиенты и партнеры взаимодействуют с системой:

- **Сайт** — веб-интерфейс компании SuperSurance с формой подачи заявки на расчет страховой премии
- **Мобильное приложение** — нативное или кроссплатформенное приложение для клиентов
- **Партнерская сеть продаж** — внешние партнеры, интегрированные через API

Все каналы отправляют запросы по протоколу **HTTPS** и получают ответы в унифицированном формате (JSON).

---

### 3.2. Точка входа — API Gateway

**API Gateway** — единая точка входа для всех внешних запросов. Выполняет следующие функции:

- **Маршрутизация** — направляет запросы к соответствующим доменным сервисам
- **Rate Limiting** — ограничение частоты запросов для защиты от перегрузки
- **Базовая аутентификация** — проверка API-ключей, токенов, сертификатов
- **Унификация запросов** — приведение запросов от разных каналов к единому формату
- **SSL-терминация** — завершение HTTPS-соединений
- **Логирование и мониторинг** — сбор метрик по входящему трафику

API Gateway **не содержит бизнес-логики** и не знает о внутренней структуре системы. Он работает только на уровне маршрутизации и безопасности.

---

### 3.3. Доменные сервисы (Domain Services)

Система разделена на **4 доменных сервиса**, каждый из которых отвечает за свою предметную область и имеет собственную базу данных.

#### 3.3.1. Домен управления клиентами (Customer Domain)

**Сервис управления клиентами (Customer Service)** отвечает за:
- Ведение единой клиентской базы (CRM-функциональность)
- Хранение персональных данных страхователей (ФИО, паспорт, водительское удостоверение, контакты)
- Управление информацией о водителях (стаж, возраст, история)
- Верификацию и валидацию клиентских данных
- Хранение истории обращений и изменений

**Структура БД (Customer DB):**
- Таблица `clients` — основные данные клиента (id, ФИО, дата рождения, паспортные данные, телефон)
- Таблица `drivers` — данные водителей (id, client_id, номер удостоверения, стаж)
- Таблица `client_history` — история изменений и обращений (id, client_id, тип изменения, дата)

**API эндпоинты:**
- `GET /api/clients/{id}` — получить данные клиента
- `POST /api/clients` — создать нового клиента
- `PUT /api/clients/{id}` — обновить данные клиента
- `GET /api/clients/{id}/drivers` — получить список водителей клиента

---

#### 3.3.2. Домен расчета и сопровождения предложений (Proposal Domain)

**Сервис расчета и сопровождения предложений (Proposal Service)** — ключевой сервис системы, выполняющий роль **оркестратора** процесса расчета премии. Отвечает за:

- Прием заявок на расчет премии от API Gateway
- Оркестрацию процесса расчета (запрос данных из других сервисов)
- Применение формулы расчета с учетом тарифов и внешних данных
- Сохранение и управление выданными предложениями (quotes)
- Генерацию уникальных ценовых предложений для клиентов

**Структура БД (Proposal DB):**
- Таблица `proposals` — основные данные предложения (id, client_id, vehicle_id, calculated_premium, status, created_at)
- Таблица `proposal_details` — детали расчета (id, proposal_id, примененные тарифы, внешние данные)
- Таблица `vehicles` — данные транспортных средств (id, VIN, марка, модель, год выпуска)

**API эндпоинты:**
- `POST /api/proposals/calculate` — рассчитать премию (основной endpoint)
- `GET /api/proposals/{id}` — получить детали предложения
- `GET /api/proposals?client_id={id}` — список предложений клиента
- `PUT /api/proposals/{id}/status` — изменить статус предложения

**Роль оркестратора:** Proposal Service при расчете премии последовательно запрашивает данные у Customer Service (данные клиента), Product Service (тарифы) и Integration Service (внешние данные), выполняет расчет по формуле и сохраняет результат.

---

#### 3.3.3. Домен управления продуктами и тарифами (Product Domain)

**Сервис управления продуктами и тарифами (Product Service)** отвечает за:

- Управление страховыми продуктами (КАСКО, ОСАГО и др.)
- Хранение тарифных планов и формул расчета
- Управление правилами и коэффициентами
- Версионирование тарифов (история изменений)
- A/B тестирование разных тарифных планов

**Структура БД (Product DB):**
- Таблица `products` — продукты (id, название, описание, статус)
- Таблица `tariffs` — тарифы (id, product_id, базовая ставка, коэффициенты)
- Таблица `tariff_rules` — правила применения тарифов
- Таблица `tariff_versions` — история изменений тарифов

**API эндпоинты:**
- `GET /api/products` — список продуктов
- `GET /api/products/{id}/tariffs` — тарифы для продукта
- `GET /api/tariffs/{id}/calculate?params=...` — получить параметры для расчета
- `POST /api/tariffs` — создать новый тариф (административный)

---

#### 3.3.4. Домен мониторинга портфеля (Portfolio Domain)

**Сервис мониторинга портфеля (Portfolio Service)** отвечает за:

- Мониторинг застрахованных транспортных средств
- Аналитику по портфелю (статистика, отчеты)
- Отслеживание рисков и убыточности
- Управление продлением полисов
- Формирование отчетов для руководства

**Структура БД (Portfolio DB):**
- Таблица `policies` — полисы (id, proposal_id, client_id, vehicle_id, start_date, end_date, premium)
- Таблица `portfolio_analytics` — агрегированные данные для отчетов
- Таблица `risk_metrics` — метрики рисков по портфелю

**API эндпоинты:**
- `GET /api/portfolio/summary` — сводка по портфелю
- `GET /api/portfolio/policies?client_id={id}` — полисы клиента
- `GET /api/portfolio/analytics?period=...` — аналитика за период
- `POST /api/portfolio/policies/{id}/renew` — продлить полис

---

### 3.4. Домен интеграций (Integration Domain)

**Интеграционный сервис (Integration Service)** — централизованный сервис для взаимодействия с внешними платными API партнеров. Выделен в отдельный домен, так как внешние интеграции являются **сквозной concern**, не принадлежащей конкретному бизнес-домену.

**Функции:**
- Централизованное взаимодействие с внешними платными API
- Кэширование ответов внешних сервисов для экономии бюджета
- Anti-Corruption Layer (ACL) — трансформация внешних данных во внутренние модели
- Управление лимитами и квотами внешних API
- Обработка ошибок и retry-логика
- Мониторинг вызовов внешних API

**Внутренняя структура:**
- **Менеджер кэша (Cache Manager)** — проверяет наличие данных в Redis перед вызовом внешнего API, реализует паттерн Cache-Aside
- **Клиенты партнерских API (Partner API Clients)** — специфичные адаптеры для каждого партнера (RepairHistoryClient, MarketValueClient, FinesClient, AntifraudClient)
- **Anti-Corruption Layer (ACL)** — трансформирует "сырые" DTO от партнеров во внутренние модели SuperSurance
- **Механизмы отказоустойчивости** — Timeout, Retry, Circuit Breaker

**Кэш (Redis):**
- Распределенный кэш Redis/Memcached для хранения ответов партнеров
- TTL: 24-48 часов (в зависимости от типа данных)
- Общий для всех доменных сервисов (так как кэш внешних данных не принадлежит конкретному домену)

**API эндпоинты (внутренние, для других сервисов):**
- `GET /api/integration/vehicle-history?vin={vin}` — история ремонта ТС
- `GET /api/integration/vehicle-value?vin={vin}` — рыночная стоимость ТС
- `GET /api/integration/driver-fines?license={license}` — история штрафов водителя
- `GET /api/integration/antifraud?client_id={id}` — проверка по антифрод-системе

**Важно:** Integration Service является **Open Host Service** — к нему могут обращаться все остальные доменные сервисы (Proposal, Portfolio, Customer) для получения внешних данных. Прямой вызов внешних API другими сервисами **запрещен**.

---

### 3.5. Внешние платные сервисы (Partner APIs)

Четыре внешних системы-партнера, предоставляющие данные для расчета премии:

- **История ремонта ТС** — данные о ремонтах и повреждениях автомобиля
- **Рыночная стоимость ТС** — оценка текущей рыночной стоимости автомобиля
- **История штрафов** — данные о штрафах водителя (ГИБДД или агрегаторы)
- **Антифрод система** — проверка клиента на причастность к мошенничеству

Все партнеры предоставляют REST API, требуют аутентификацию (API-ключи) и являются платными (оплата за каждый запрос).

## 4. Потоки данных и взаимодействия

### 4.1. Основной сценарий: Расчет премии

1. **Клиент** (с сайта, из мобильного приложения или от партнера) отправляет запрос на расчет через **API Gateway**
2. **API Gateway** выполняет аутентификацию, проверяет rate limit и маршрутизирует запрос в **Proposal Service**
3. **Proposal Service** начинает процесс оркестрации:
   - Запрашивает данные клиента у **Customer Service** (`GET /api/clients/{id}`)
   - Запрашивает актуальные тарифы у **Product Service** (`GET /api/products/kasko/tariffs`)
   - Запрашивает внешние данные у **Integration Service**:
     - История ремонта (`GET /api/integration/vehicle-history?vin={vin}`)
     - Рыночная стоимость (`GET /api/integration/vehicle-value?vin={vin}`)
     - История штрафов (`GET /api/integration/driver-fines?license={license}`)
     - Антифрод-проверка (`GET /api/integration/antifraud?client_id={id}`)
4. **Integration Service** для каждого запроса:
   - Проверяет кэш в **Redis**
   - При Cache Miss вызывает внешний API партнера
   - Трансформирует ответ через **ACL** во внутреннюю модель
   - Сохраняет результат в кэш (TTL 24-48 часов)
   - Возвращает данные в Proposal Service
5. **Proposal Service** выполняет расчет по формуле: `premium = base_rate * coefficients * external_factors`
6. **Proposal Service** сохраняет предложение в свою БД
7. Результат возвращается клиенту через **API Gateway**

### 4.2. Межсервисное взаимодействие

- **Тип коммуникации:** Синхронный REST API (HTTP/HTTPS)
- **Формат данных:** JSON (DTO — Data Transfer Objects)
- **Аутентификация между сервисами:** API-ключи или JWT-токены (внутренняя сеть)
- **Таймауты:** 5 секунд на каждый вызов сервиса
- **Retry-логика:** 3 попытки при ошибках 5xx
- **Трассировка:** Request ID передается через все сервисы (header `X-Request-ID`)

### 4.3. Принципы взаимодействия

- **Database per Service:** Каждый сервис имеет свою БД, прямой доступ к БД другого сервиса запрещен
- **API-first:** Все межсервисные взаимодействия только через публичные API
- **Изоляция контекста:** Внешние данные трансформируются через ACL перед использованием
- **Единая точка интеграции:** Все внешние API вызовы только через Integration Service

## 5. Ключевые архитектурные решения и их обоснование

### 5.1. Почему микросервисы, а не модульный монолит?

- **Закон Конвея:** архитектура должна отражать организационную структуру (4 команды = 4 сервиса)
- **Независимость команд:** каждая команда может выбирать технологии, релизить независимо
- **Масштабируемость:** можно масштабировать только нагруженные сервисы (например, Proposal при высоком спросе)
- **Отказоустойчивость:** падение одного сервиса не выводит из строя всю систему

### 5.2. Почему Database per Service?

- **Изоляция данных:** сервисы не имеют прямого доступа к БД друг друга
- **Гибкость схем:** каждый домен может оптимизировать свою БД под свои нужды (PostgreSQL для транзакционных данных, ClickHouse для аналитики)
- **Независимое развертывание:** изменения в схеме одной БД не ломают другие сервисы
- **Масштабирование:** можно реплицировать только нагруженные БД

### 5.3. Почему единый Redis для кэша, а не per Service?

- **Природа данных:** кэш внешних API не принадлежит конкретному домену, это общий ресурс
- **Экономия памяти:** избегается дублирование одних и тех же данных в разных инстансах Redis
- **Консистентность:** обновление кэша в одном месте сразу видно всем сервисам
- **Простота управления:** один Redis-кластер проще администрировать
- **Cost Optimization:** один большой кластер дешевле нескольких маленьких

### 5.4. Почему Integration Service выделен отдельно?

- **DRY (Don't Repeat Yourself):** логика кэширования и ACL не дублируется в каждом сервисе
- **Централизованное управление квотами:** видно, сколько запросов к каждому партнеру осталось
- **Безопасность:** API-ключи партнеров хранятся в одном защищенном месте
- **Изоляция сбоев:** проблемы с внешними API не влияют на бизнес-логику доменных сервисов

### 5.5. Почему Proposal Service является оркестратором?

- **Владелец процесса:** процесс "Расчет и выдача предложения" — это отдельная бизнес-транзакция
- **API Gateway не должен знать бизнес-логику:** маршрутизация ≠ оркестрация
- **Синхронность:** клиент ждет результат в реальном времени
- **Простота:** паттерн оркестрации проще для понимания и отладки на текущем этапе

## 6. Глоссарий терминов

| Термин | Описание |
|--------|----------|
| **ACL (Anti-Corruption Layer)** | Слой трансформации, защищающий внутреннюю модель данных от внешних форматов |
| **API Gateway** | Единая точка входа для всех внешних запросов |
| **Cache-Aside** | Паттерн кэширования, при котором приложение сначала проверяет кэш, а при отсутствии данных загружает их из источника |
| **Circuit Breaker** | Паттерн отказоустойчивости, предотвращающий повторные вызовы неработающего сервиса |
| **Database per Service** | Паттерн, при котором каждый микросервис имеет свою собственную базу данных |
| **Domain-Driven Design (DDD)** | Подход к проектированию, основанный на предметной области бизнеса |
| **DTO (Data Transfer Object)** | Объект для передачи данных между сервисами |
| **Open Host Service** | Сервис, предоставляющий открытый API для других подсистем |
| **Оркестратор** | Сервис, координирующий выполнение бизнес-процесса путем вызова других сервисов |
| **Rate Limiting** | Ограничение частоты запросов для защиты от перегрузки |
| **Retry** | Механизм повторных попыток при временных сбоях |
| **TTL (Time To Live)** | Время жизни данных в кэше |
| **Timeout** | Максимальное время ожидания ответа от сервиса |

## 7. Метрики и характеристики системы

| Показатель | Значение |
|------------|----------|
| Общее время ответа на расчет премии | ~500-800 мс |
| Количество межсервисных вызовов при расчете | 4+ (Customer, Product, Integration x2-4) |
| Эффективность кэша | до 70% запросов к внешним API обслуживаются из кэша |
| Количество доменных сервисов | 4 (Customer, Product, Proposal, Portfolio) + 1 интеграционный |
| Количество баз данных | 5 (4 доменных + 1 кэш Redis) |
| Количество внешних партнеров | 4 (история ремонта, стоимость, штрафы, антифрод) |
