# Архитектура SuperSurance — Упражнение 3: Организация пользовательской обработки задач

> Строится поверх схемы Упражнения 2.

## 1. Контекст

Появляются новые категории пользователей системы:
- **Андеррайтеры** — вручную устанавливают премию, если автоматический расчёт невозможен: система определила высокий риск по клиенту или не сработали правила однозначного определения премии.
- **Администраторы** — настраивают продукты, просматривают данные по клиентам, ТС, расчётам, заявкам.

Также нужен механизм **push-уведомлений пользователей системы** о новых задачах, ошибках и важных событиях.

### Что меняется относительно Упражнения 2

| Аспект | Упражнение 2 | Упражнение 3 |
|---|---|---|
| Пользователи | Только клиенты и партнёры | + андеррайтеры, администраторы |
| Точки входа | API Gateway | + Back-office и внутренний шлюз (BFF) |
| Аутентификация пользователей | Нет | Identity Provider (SSO, роли) |
| Взаимодействие сервисов | Только синхронный REST | + асинхронные события через брокер |
| Результат расчёта | Всегда синхронно | Синхронно или отложенно (ручной андеррайтинг) |
| Новые сервисы | — | Underwriting Service, Notification Service |

## 2. Новые компоненты

### 2.1. Back-office (веб-приложение)
Рабочее место андеррайтеров и администраторов:
- очередь задач андеррайтинга, карточка задачи, ввод премии;
- настройка продуктов и тарифов;
- просмотр клиентов, ТС, расчётов и заявок;
- центр уведомлений (push в реальном времени и история).

### 2.2. Internal Gateway / BFF
Отдельная точка входа для back-office, не смешанная с клиентским API Gateway:
- проверка токена пользователя и роли;
- маршрутизация к сервисам;
- сборка детальных экранов из нескольких сервисов (API Composition), например карточка задачи = задача + предложение + ТС + клиент + тариф + внешние данные;
- WebSocket/SSE-канал для push-уведомлений.

Почему отдельно от API Gateway: другие пользователи, другие требования к безопасности (только внутренняя сеть/VPN), другой формат ответов.

### 2.3. Identity Provider (IdP)
SSO для сотрудников и выдача токенов (OIDC/JWT) с ролями `underwriter`, `underwriter_lead`, `admin`.
В упражнении 3 — только аутентификация и базовые роли. Полноценное управление ролями и доступами — Упражнение 5.

### 2.4. Underwriting Service + Underwriting DB
Сервис ручной обработки задач. Не знает правил риска — только обрабатывает задачи, которые ему передал расчёт.

**Ответственность:**
- приём запроса на андеррайтинг от Proposal (по событию);
- общая очередь задач: андеррайтер сам берёт задачу себе;
- защита от двойного взятия: `claim` атомарно меняет статус `NEW → IN_PROGRESS` только если задача ещё свободна (атомарный условный UPDATE, compare-and-set);
- возврат задачи в очередь, переназначение руководителем;
- контроль SLA: планировщик внутри сервиса находит просроченные задачи и публикует `UnderwritingTaskSlaBreached`;
- фиксация решения и аудит: кто, когда, какая премия, обоснование.

**Статусы задачи:** `NEW → IN_PROGRESS → DONE`; `IN_PROGRESS → NEW` (вернул в очередь).

**Структура БД:**
- `tasks` — id, proposal_id, reason (HIGH_RISK / NO_RULE_MATCH), status, assignee_id, sla_due_at, created_at;
- `decisions` — id, task_id, decision (PRICED / DECLINED), premium, comment, decided_by, decided_at;
- `task_history` — журнал всех действий по задаче (аудит).

Андеррайтеры как пользователи хранятся в IdP, в Underwriting — только `assignee_id`.

**Основные операции (через Internal Gateway):** очередь задач, `claim` (взять себе), `release` (вернуть), `decision` (установить премию / отказать).

### 2.5. Message Broker (Kafka / RabbitMQ)
Асинхронный обмен доменными событиями. Нужен, чтобы:
- клиентский расчёт не зависел от доступности back-office-сервисов;
- уведомления строились на событиях, а не на опросе сервисов.

Надёжность публикации — **Transactional Outbox**: сервис в одной транзакции пишет изменение и запись в таблицу `outbox`, отдельный relay публикует её в брокер. Потребители идемпотентны (учёт обработанных `event_id`).

### 2.6. Notification Service + Notification DB
Принимает события, определяет получателей и доставляет уведомления.

- **Маршрутизация «событие → кому»**: новая задача — роли `underwriter`; нарушение SLA — `underwriter_lead`; ошибка интеграции и неудавшийся расчёт — `admin`. Не «всем обо всём».
- **Доставка:** in-app push: Notification Service → Internal Gateway (держит WebSocket/SSE-соединения с пользователями) → Back-office.
- **Хранение:** `notifications` (id, recipient_user_id / recipient_role, type, payload, created_at, read_at) — история и непрочитанные, если пользователь был офлайн.
- **Расширяемость каналов:** SMS и e-mail в Упражнении 5 добавляются как новые каналы этого же сервиса, а не как отдельный сервис.

## 3. Изменения в существующих сервисах

### Proposal Service
- **Правило «авторасчёт невозможен» остаётся в Proposal** (там же, где расчёт): высокий риск-скор или ни одно правило не дало однозначной премии.
- **Новые статусы предложения:**
  - `CALCULATED` — рассчитано автоматически;
  - `PENDING_UNDERWRITING` — ждёт андеррайтера;
  - `PRICED_MANUALLY` — премию установил андеррайтер;
  - `DECLINED` — отказ (допущение, см. раздел 6);
  - `WAITING_EXTERNAL_DATA` — партнёр недоступен, ждём данных;
  - `CALCULATION_FAILED` — исчерпаны попытки получить данные.
- **Ответ клиенту:** `200` с премией при авторасчёте или `202 Accepted` с id предложения и статусом. Канал узнаёт результат через `GET /api/proposals/{id}` (опрос). Уведомление клиента по SMS/e-mail — Упражнение 5.
- Публикует: `UnderwritingRequested`, `ProposalCalculationFailed`. Потребляет: `UnderwritingCompleted`.
- Добавлен outbox.

### Integration Service
- Redis считаем собственностью Integration Service: кроме него кэшем никто не пользуется (уточнение к разд. 5.3 упр. 2).
- Публикует `PartnerUnavailable` — источник уведомлений об ошибках для администраторов. Публикует напрямую, без outbox: своей транзакционной БД у сервиса нет, а потеря отдельного уведомления об ошибке не критична.

### Product Service
- Административные эндпоинты (создание и изменение продуктов и тарифов) доступны только через Internal Gateway с ролью `admin`.

### Customer, Portfolio
- Без изменений. Администратор читает их через Internal Gateway.

## 4. Сценарии

### 4.1. Ручной расчёт андеррайтером
1. Клиент отправляет заявку → API Gateway → Proposal.
2. Proposal собирает данные (Customer, Product, Integration), считает риск-скор; правило определяет, что авторасчёт невозможен.
3. Proposal сохраняет предложение в статусе `PENDING_UNDERWRITING` и в той же транзакции пишет `UnderwritingRequested` в outbox. Клиенту возвращается `202 Accepted`.
4. Underwriting получает событие, создаёт задачу `NEW`, публикует `UnderwritingTaskCreated`.
5. Notification отправляет push всем андеррайтерам онлайн и сохраняет уведомление.
6. Андеррайтер открывает задачу в Back-office (карточка собирается в BFF), делает `claim`, вводит премию и обоснование.
7. Underwriting сохраняет решение и аудит, публикует `UnderwritingCompleted`.
8. Proposal переводит предложение в `PRICED_MANUALLY` с премией. Клиент видит результат при следующем запросе статуса.

### 4.2. Партнёр недоступен
1. Integration после retry и срабатывания Circuit Breaker возвращает ошибку и публикует `PartnerUnavailable`.
2. Proposal переводит предложение в `WAITING_EXTERNAL_DATA`. Планировщик внутри Proposal повторяет расчёт для таких предложений (допущение: каждые 15 минут, до 4 попыток).
3. Notification уведомляет администраторов.
4. Если после всех попыток данных нет — `CALCULATION_FAILED` и событие `ProposalCalculationFailed`.

Андеррайтеру такие заявки не передаются: у него тоже нет недостающих внешних данных.

### 4.3. Нарушение SLA
Планировщик Underwriting находит задачи с истёкшим `sla_due_at` → `UnderwritingTaskSlaBreached` → push руководителю андеррайтеров.

### 4.4. Администратор настраивает продукт
Back-office → Internal Gateway (проверка роли `admin`) → Product Service.

## 5. События

| Событие | Публикует | Потребители |
|---|---|---|
| `UnderwritingRequested` | Proposal | Underwriting |
| `UnderwritingTaskCreated` | Underwriting | Notification |
| `UnderwritingTaskSlaBreached` | Underwriting | Notification |
| `UnderwritingCompleted` | Underwriting | Proposal |
| `ProposalCalculationFailed` | Proposal | Notification |
| `PartnerUnavailable` | Integration | Notification |

## 6. Допущения и границы

- Расчёт и сущность ТС остаются в Proposal, как в Упражнении 2.
- Отказ в страховании (`DECLINED`) — наше расширение; задание говорит только об установке премии.
- Технический мониторинг и алертинг (метрики, логи) — вне рамок; Notification отвечает только за бизнес-уведомления пользователей.
- Уведомления клиентов (SMS, e-mail) и полноценный RBAC — Упражнение 5.
- Сводные списки «заявки + клиент + ТС + продукт» для администратора — Упражнение 4.
