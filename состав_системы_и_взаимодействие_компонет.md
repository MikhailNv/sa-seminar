# Потоки данных и элементы схемы: бизнес-функция каждого элемента

**Что это за решение.** Обособленный подключаемый модуль отправки уведомлений: у него собственный внешний контракт API, собственные базы данных и тенантность (`tenant_id`). Общих таблиц с системами-потребителями нет, поэтому модуль можно отделить от конвейера расчёта и подключить к любой другой системе компании без её изменения — конвейер остаётся просто одним из клиентов API.

# 0. Элементы схемы и их бизнес-функция

**Потребители**

| Элемент | Бизнес-функция | Что делает |
|---|---|---|
| Конвейер расчёта премии | Инициирует уведомление клиенту о готовности расчёта | Формирует запрос: кому, что, каким каналом, когда |
| Другие ИТ-системы | Любая система компании может «попросить» отправить уведомление | Тот же контракт, что у конвейера |
| Back-office | Рабочее место администратора: шаблоны, кампании, мониторинг | Управляет контентом, настройками и рассылками |
| Клиенты компании | Получатели сообщений и собеседники помощника | Читают сообщения в канале, ленте, чате |

**API-слой**

| Элемент | Бизнес-функция | Что делает |
|---|---|---|
| API Gateway | Не пустить чужого и не дать одному потребителю забрать всю мощность | Проверяет подпись токена по ключам Keycloak (кэш), читает права из токена, считает квоту в Redis, маршрутизирует по статической конфигурации, принимает вебхуки провайдеров. **Доменные сервисы на каждый запрос не вызывает** |
| Notification API | Единая точка приёма: «отправь вот это вот этому» | Спрашивает владельцев данных и передаёт сообщение в `delivery-service`; своей БД нет. Один код — **два независимых развёртывания**: point (быстрый приём) и batch (массовые задания). **Параллельно:** `content-service` + `config-service` (+ `audience-service`, если получатель — один контакт). **Затем последовательно:** `audience-service` (резолв группы → согласия) → `delivery-service` (последним) |
| Query API | Дать потребителю увидеть судьбу его сообщений | Отдаёт статусы, историю и ошибки — **синхронно** из `journal-service`. События не слушает: «подписка» здесь — это запись адреса потребителя в `config-service`, а события по ней отправляет `journal-service` |
| Bell Inbox API | «Колокольчик»: показать уведомления внутри интерфейса клиента | Отдаёт ленту, счётчик непрочитанных, отмечает прочитанным, пушит новые по WebSocket. Читает данные из `journal-service` и события из Kafka; своей БД нет |
| Admin API | Собрать экраны back-office из данных владельцев | Собирает ответ из `content-service`, `config-service`, `audience-service`, `journal-service`, `delivery-service`. Своей БД нет, данные не копирует, ходит только по контрактам владельцев и только в своём тенанте |

> **Про Gateway подробнее.** На каждый запрос он **не обращается к доменным сервисам**: подпись токена проверяется по ключам Keycloak (загружаются один раз, дальше кэш 5–15 мин), права читаются из самого токена, израсходованная квота считается в Redis, маршрут берётся из статической конфигурации. Значения квот и лимитов действительно задаются в `config-service`, но шлюз получает их **заранее** — при старте и по событию «настройки изменились». Иначе на каждый запрос он зависел бы от домена и стал бы точкой отказа для всего трафика.

> **Про «два деплоймента» Notification API.** Это один сервис — один код, один контракт, одна логика валидации — но запущенный **двумя независимыми группами экземпляров**:
> * point-деплоймент обслуживает `/v1/notifications`: низкая задержка, высокий RPS, много реплик;
> * batch-деплоймент обслуживает `/v1/batches`: долгие запросы, большие тела, меньше реплик, больше памяти.
>
> У каждого свои лимиты CPU/памяти, свои квоты, пулы соединений, автоскейлинг и график обновлений. Смысл — требование «массовая рассылка не должна влиять на точечную отправку»: даже если batch-экземпляры загружены под потолок, point продолжает принимать запросы. Дублирования кода при этом нет: исправление в общей валидации выкатывается одним артефактом в оба деплоймента.

> **Что значит «валидирует и передаёт в доставку».** Notification API ничего не создаёт и не хранит: он спрашивает владельцев данных и, если все ответили «можно», отдаёт сообщение в `delivery-service`.
>
> **Параллельно** — независимые проверки, каждая отвечает из кэша:
> * `content-service` — шаблон существует, опубликован и совместим с каналом; вложения загружены и проверены антивирусом;
> * `config-service` — канал включён для тенанта, квота не исчерпана;
> * `audience-service` — согласие, opt-out и частотный лимит по получателю — **только если получатель один контакт**.
>
> **Последовательно:**
> 1. `audience-service` — резолв группы в контакты — **только если получатель группа** (без этого нельзя проверить согласия по конкретным людям);
> 2. `audience-service` — проверка согласий, opt-out и лимитов по каждому контакту;
> 3. `delivery-service` — приём сообщения; **всегда последним**, потому что только он пишет в БД.
>
> Итого две ветки:
> * **один контакт:** `content` ‖ `config` ‖ `audience` → `delivery`;
> * **группа:** `content` ‖ `config` → резолв группы → проверка согласий → `delivery`.
>
> Почему так: сначала дешёвые кэшируемые проверки (шаблон, канал), потом дорогая (резолв до 5000 контактов), запись — последней. Если хоть одна проверка не прошла, не создаётся ничего, а клиент получает 422/403/409/429/503. Рендер здесь не выполняется — он произойдёт позже, внутри `delivery-service`.
>
> **Про бизнес-данные.** Всё, что подставляется в шаблон (ФИО, сумма премии, номер полиса), приходит в самом запросе потребителя. Notification API не ходит за этими данными в CRM или конвейер — он лишь проверяет, что данные есть и что получателю можно писать.

> **Про Query API.** Он **ничего не слушает и ни на что не подписывается**: это read-only API, который по запросу потребителя синхронно спрашивает `journal-service`. «Подписка на события» в его маршрутах — это не подписка самого сервиса, а **регистрация адреса потребителя** в `config-service`; сами события по этому адресу отправляет `journal-service` (у него для этого есть очередь и повторы).
>
> Для сравнения: `Bell Inbox API` действительно читает события из Kafka — ему нужно мгновенно пушить новые уведомления в открытый интерфейс. `Query API` этого не делает: потребитель сам решает, когда спросить статус.

> **Про Bell Inbox API (почему «bell inbox»).** Название — из интерфейсной метафоры: «колокольчик» в шапке приложения со счётчиком непрочитанных и лентой уведомлений (**inbox** — «входящие», как в почте). Это API самой ленты, а не отдельный канал доставки: доставляет `delivery-service` (канал `bell`), а `Bell Inbox API` показывает результат пользователю.
>
> **Артефакты встройки.** Для сторонних систем выпускается единый набор: JS-виджет (лента и счётчик), backend-модуль (обёртка над API, приём событий) и Docker-образ. Система, встроившая набор, становится **самостоятельным каналом доставки**: `Bell Inbox API` отдаёт ей ленту, а `delivery-service` считает её таким же каналом, как SMS или e-mail. Новый канал не требует перестройки ядра — только регистрации в `config-service`.
>
> **Что делает:**
> * отдаёт ленту уведомлений пользователя (курсорная пагинация; `userId` берётся из токена, а не из запроса);
> * отдаёт счётчик непрочитанных для бейджа;
> * отмечает прочитанным один элемент или все сразу;
> * убирает элемент из ленты (мягко — журнал и retention не страдают);
> * держит WebSocket/SSE-соединения и мгновенно пушит новые элементы.
>
> **С какими сервисами взаимодействует:** `journal-service` — единственный доменный сервис, где лежит лента (он же хранит статусы, историю и аудит); события `notification.created` читает из Kafka, чтобы пушить в реальном времени; Redis — только счётчики непрочитанных и присутствие пользователя (инфраструктура, не домен).
>
> **Чего не делает:** не создаёт уведомления, не рендерит контент, не хранит данные у себя, не показывает чужие `userId`.

> **Про Admin API.** Это **BFF** — «бэкенд для фронтенда» админки, а не универсальная ручка «достать любые данные». Он не читает БД и не копирует данные себе: на каждый экран делает 1–4 вызова к владельцам и отдаёт фронтенду уже собранный ответ.
>
> **С кем взаимодействует:**
> * `content-service` — шаблоны, версии, предпросмотр, файлы;
> * `config-service` — каналы, провайдеры, квоты, лимиты, сроки хранения, флаги;
> * `audience-service` — группы, сегменты, согласия;
> * `journal-service` — журнал, статусы, мониторинг, аудит;
> * `delivery-service` — состояние доставки, здоровье каналов, пауза/отмена рассылки, повторная отправка.
>
> **Чего не может:** выйти за пределы своего тенанта; прочитать чужую таблицу напрямую; увидеть секреты провайдеров (они в Vault); получить данные, которые владелец не отдаёт по контракту; выполнить произвольный запрос «дай всё».
>
> **Зачем именно BFF:** обмен пользовательской сессии на сервисные токены, агрегация 2–4 вызовов в один ответ для экрана, сокрытие внутренних контрактов от браузера и аудит действий администратора в одном месте.
>
> **Изоляция от нагрузки.** `Admin API` — отдельный деплоймент и отдельный пул: ни поток точечных уведомлений, ни массовая рассылка не отбирают у него ресурсы. Если доменный сервис недоступен (например, журнал), экран показывает «данные недоступны», но управление шаблонами, каналами и группами продолжает работать — администрирование не блокируется отправкой.

**Домен**

| Элемент | Бизнес-функция | Что делает |
|---|---|---|
| content-service | «Как выглядит сообщение»: шаблон, вёрстка, файлы | Ведёт шаблоны и версии (черновик → публикация), отдаёт шаблон для проверки и рендера, рендерит под канал, принимает файлы по presigned-ссылке (антивирус, TTL). **Хранилища:** PostgreSQL (шаблоны, метаданные файлов), Redis (кэш шаблонов), S3 (файлы и отрендеренный контент). **Публикует:** `template.published`, `file.scanned` |
| audience-service | «Кому можно писать»: получатели и согласия | Резолвит группу в контакты, проверяет согласие, opt-out (отписку) и частотные лимиты, отвечает по каждому контакту `allow` / `deny` с причиной. **Хранилища:** PostgreSQL (группы, состав, согласия, история), Redis (кэш состава групп, счётчики лимитов). **Публикует:** `preferences.changed`, `recipients.imported` |
| delivery-service | Ядро: гарантировать, что сообщение уйдёт провайдеру | Фиксирует сообщение, доставки и outbox **одной транзакцией**, держит очередь и приоритеты, просит рендер у `content-service`, ретраит, выбирает провайдера, вызывает адаптеры каналов. **Хранилища:** PostgreSQL (сообщения, доставки, outbox, задания), Kafka (события), RabbitMQ (очереди каналов, повторы, DLQ), Redis (идемпотентность, отложенные, блокировки). **Публикует:** `notification.*`, `batch.*` |
| journal-service | «Что и когда произошло»: журнал, статусы, аудит | Материализует историю из событий Kafka, принимает квитанции провайдеров, отдаёт статусы, историю и поиск, хранит ленту «колокольчика» и аудит, отправляет webhook-подписки, ведёт retention. **Хранилища:** PostgreSQL (журнал, квитанции, лента, аудит), OpenSearch (поиск), S3 (архив), Redis (дедуп квитанций, unread). **Потребляет:** `notification.*`, `audit.*` |
| config-service | Единственный источник правды о настройках | Хранит каналы, провайдеров, маршруты «канал → провайдеры», квоты, лимиты, retention, флаги и webhook-подписки, проверяет целостность (нельзя включить канал без провайдера). **Хранилище:** только PostgreSQL (плюс собственная таблица `outbox`). **Публикует:** `config.changed`. **Redis, S3, OpenSearch не использует** — кэш держат читатели |
| assistant-service | Виртуальный помощник | Принимает сообщения из мессенджеров, ведёт диалог, ищет в базе знаний (RAG), вызывает LLM, отправляет ответ через `delivery-service`. Индексирует справочные документы с файловой шары и из опубликованных API. **Хранилища:** PostgreSQL (диалоги, промпты, реестр знаний), векторная БД (эмбеддинги), S3 (снапшоты документов), Redis (сессии, дедуп, кэш), Kafka (события диалога) |

> **Про content-service и его хранилища.**
> * **PostgreSQL** — источник правды: шаблоны, их версии (черновик / активная), локали, условия, связи с файлами; метаданные файлов и статус антивируса. Транзакции нужны для публикации версии и защиты от одновременного редактирования.
> * **Redis** — кэш опубликованных шаблонов (`tpl:{code}:{version}`) и активной версии по коду шаблона: рендер и приём не должны ходить в БД на каждое сообщение. Сбрасывается событием `template.published`.
> * **S3/MinIO** — тела файлов (изображения, вложения) и отрендеренный контент `rendered/{message_id}/{channel}` с TTL: большие объёмы не должны жить в операционной БД. Клиент грузит файл напрямую по presigned-ссылке, сервис только выдаёт разрешение и проверяет результат.
> * **Kafka** — публикует `template.published` и `file.scanned`: по этим событиям другие сервисы сбрасывают кэш, а журнал фиксирует изменение.
>
> Не использует: OpenSearch (это журнал), RabbitMQ (это доставка), векторную БД и файловую шару (это помощник).

> **Про audience-service: согласия и лимиты.**
> * **Opt-out (отписка)** — запрет на коммуникации с конкретным получателем. Бывает полный («не писать вообще»), по каналу («SMS нельзя, e-mail можно») и по типу сообщения («маркетинг запрещён, сервисные уведомления — можно»). Это **не удаление контакта**: человек остаётся в базе, но отправка для него блокируется. Согласие и отказ имеют юридический вес (реклама требует предварительного согласия), поэтому хранится история изменений, а не только текущий флаг.
> * **Частотные лимиты (frequency capping)** — ограничение числа сообщений одному человеку за период: не более 1 маркетингового в сутки, не более N в неделю по каналу. Защищают от спама, снижают отписки и расходы на SMS. Транзакционные сообщения («расчёт готов») идут **вне** маркетингового лимита, иначе клиент не получит важное.
>
> **Как применяется:** на приёме `audience-service` возвращает по каждому контакту `allow` или `deny` с причиной (`opt_out`, `frequency_limit`, `no_consent`). Отсеянные не пропадают молча: попадают в ответ `excluded[]` с причиной и видны в оценке объёма кампании.
>
> **Хранилища и шина:**
> * **PostgreSQL** — группы и их состав, контакты, согласия с историей, правила лимитов. Нужны связи «многие-ко-многим», транзакции при импорте и юридически значимая история.
> * **Redis** — кэш состава групп (резолв без запроса в БД) и счётчики лимитов: ключ `freq:{tenant}:{recipient}:{channel}:{period}` → число с TTL на окно.
> * **Kafka** — публикует `preferences.changed` и `recipients.imported`; слушает события отправки, чтобы увеличивать счётчик только по реально отправленным сообщениям (неудачные попытки лимит не съедают).
>
> Не использует: S3 (файлы — это `content-service`), OpenSearch (журнал), RabbitMQ (доставка).

> **Про delivery-service и его ресурсы.** Это единственный сервис, который создаёт сообщение, поэтому у него самая насыщенная «сантехника».
> * **PostgreSQL** — агрегат доставки: `messages` (сообщение), `deliveries` (строка на канал), `outbox` (событие к публикации), `batch_job` / `batch_chunk` (массовые задания), `schedules` (отложенные). Сообщение и outbox пишутся **одной транзакцией** — это и есть гарантия «принято = не потеряется».
> * **Kafka** — события: публикует `notification.requested / rendered / sent / failed`, читает `notification.requested`, `notification.due`, `batch.requests`, `batch.commands`. Даёт буфер при пиках, at-least-once и разделение пулов point/batch.
> * **RabbitMQ** — рабочие очереди отправки: `send.{channel}.{provider}` с приоритетом (транзакционные выше маркетинговых), `retry.{channel}` с TTL+DLX (повтор через 1 мин / 5 мин / 15 мин / 1 ч / 6 ч) и `dlq.{channel}` после 5 попыток. Здесь же адаптеры соблюдают технический лимит провайдера.
> * **Redis** — быстрое состояние без транзакций: ключи идемпотентности (`idem:...`, SETNX + TTL 24 ч, дублируются в PostgreSQL), ZSET отложенных отправок (`schedule:due`), блокировки доставки (`lock:{delivery_id}`), чтобы два воркера не отправили дважды.
>
> **Зачем два брокера.** Kafka — журнал событий (долгое хранение, повторное чтение, чанки batch); RabbitMQ — рабочие очереди с приоритетами, отложенными повторами и DLQ. С одним брокером приоритеты и повторы пришлось бы писать вручную.
>
> **Термины.** *Outbox* — таблица исходящих событий, которая пишется в одной транзакции с сообщением; отдельный процесс публикует её в Kafka, поэтому «принято» и «событие существует» — одно и то же. *DLQ* (dead letter queue) — очередь, куда попадают сообщения после исчерпания попыток: они не теряются, а видны для разбора.
>
> Не использует: S3 напрямую (рендер и файлы — `content-service`), OpenSearch (журнал).

> | Таблица | Что содержит | Зачем отдельно |
> |---|---|---|
> | `messages` | одно сообщение: `message_id`, тенант, шаблон и его версия, хэш данных, состояние, ключ идемпотентности, `send_at`, `trace_id` | якорь идемпотентности и карточка «одно уведомление»; не зависит от числа каналов |
> | `deliveries` | строка на канал и получателя: адрес, состояние отправки, число попыток, провайдер, его идентификатор сообщения | у каждого канала свой жизненный цикл, свои попытки и своя ошибка; один общий статус это не выражает |
> | `outbox` | событие к публикации: тип, агрегат, тело, время, признак публикации | техническая очередь **внутри транзакции**; живёт часы, а не годы |
>
> Пример: одно сообщение в SMS и push одному человеку → **1** строка в `messages`, **2** в `deliveries`, дальше по строке `outbox` на каждое событие (`requested`, `rendered`, `sent`).
>
> **Кто пишет.** Только сам `delivery-service`: `INSERT` сообщения и доставок при приёме, `UPDATE` при каждой попытке отправки, `INSERT` в `outbox` — в той же транзакции, что и изменение агрегата. Другие сервисы и API-слой в эти таблицы не пишут.
>
> **Как outbox попадает в Kafka.** Отдельный процесс (Debezium — читает журнал транзакций PostgreSQL, либо поллер) забирает строки `outbox` и публикует их в Kafka. Он **только читает**: в базу не пишет, строки не удаляет. Очистка опубликованных строк — отдельная задача по TTL. Debezium видит лишь закоммиченные изменения и в порядке коммита, поэтому события одного сообщения не перемешиваются.
>
> **Состояния, которыми владеет delivery-service:** `PENDING` → `RENDERING` → `QUEUED` → `SENT` | `FAILED`. Подтверждение доставки по квитанции (`DELIVERED` / `READ`) — не его зона, оно живёт в журнале.
>
> **Гарантия.** Сообщение, доставки и outbox пишутся **одной транзакцией**: либо всё, либо ничего. Поэтому «принято» (202) и «событие будет опубликовано» — одно действие, а сбой между шагами не теряет и не дублирует уведомление.

> **Про journal-service и его ресурсы.** Это «бухгалтерия» системы: всё, что произошло с сообщением, и всё, что сделали администраторы.
> * **PostgreSQL** — источник правды по истории: `journal` (карточка сообщения и каналов), `delivery_events` (каждое изменение статуса), `receipts` (сырые квитанции провайдеров), `inbox` (лента «колокольчика» по пользователям), `audit`. Партиционирование по дате, retention — по каналу.
> * **OpenSearch** — поиск и агрегаты: полнотекстовый поиск по журналу и аудиту, дашборды доставки. Индекс производный: его можно пересобрать из PostgreSQL.
> * **S3/MinIO** — архив: отцепленные партиции и выгрузки для разбора.
> * **Kafka** — потребляет `notification.requested / rendered / sent / failed / delivered / read` и `audit.*`: журнал узнаёт о событиях сам, ему не нужно опрашивать другие сервисы.
> * **Redis** — дедупликация квитанций (`dlr:{provider_message_id}`), счётчики непрочитанных для ленты, кэш активных webhook-подписок.
>
> **Операции:** приём событий из Kafka и материализация истории; приём квитанций по `/webhooks/v1/*` (проверка подписи, дедуп); выдача статуса, истории и попыток; поиск и агрегаты для мониторинга; лента «колокольчика» и отметки о прочтении; аудит; отправка webhook-событий подписчикам с повторами; retention и архив.
>
> **Чего не делает:** не создаёт и не отправляет сообщения, не хранит контент (он в S3 у `content-service`), не считает согласия и лимиты.

> **Про config-service и его ресурсы.**
> * **PostgreSQL** — единственное хранилище: `channels`, `providers`, `routes` (канал → провайдеры, приоритеты, веса, резерв), `quotas`, `limits`, `retention`, `flags`, `webhook_subscriptions`, `config_versions` (кто и когда менял) и собственная таблица `outbox`.
> * **Kafka** — публикует `config.changed`, больше ничего не слушает.
> * **Redis, S3, OpenSearch не использует.** Кэш конфигурации держат у себя читатели (`Notification API`, `delivery-service`, шлюз) и обновляют его по событию `config.changed`. Секреты webhook-подписок лежат в Vault, в таблице — только ссылка.
> * Отдельной копии настроек в Redis нет намеренно: это была бы вторая правда и риск рассинхрона. Config меняется редко и читается редко — ему достаточно PostgreSQL.
>
> **Операции:** CRUD каналов (включить/выключить для тенанта, ограничения формата), CRUD провайдеров и маршрутов, квоты тенантов, лимиты запросов (число получателей, вложений, размер), retention по каналу, feature flags, webhook-подписки, отдача снапшота конфигурации читателям, проверка целостности (нельзя включить канал без провайдера; retention не ниже минимума), история изменений.
>
> **Кто пишет:** только `Admin API` (настройки) и `Query API` (подписки потребителей). Читают все остальные.
>
> **Чего не делает:** не применяет политики сам (применяют читатели), не считает квоты (счётчики — в шлюзе и Redis), не хранит бизнес-данные.

> **Про assistant-service: ресурсы, база знаний и поиск.**
> * **PostgreSQL** — диалоги, сессии, сообщения, оценки, версии промптов, реестр документов и версий индекса.
> * **Векторная БД** — эмбеддинги чанков и метаданные (документ, раздел, услуга, дата, версия) — по ним фильтруется поиск.
> * **S3/MinIO** — снапшоты исходных документов: чтобы можно было переиндексировать и объяснить, на каком тексте основан ответ.
> * **Redis** — кэш контекста сессии, дедупликация входящих сообщений, кэш ответов LLM, лимиты на пользователя.
> * **Kafka** — `assistant.requested` (входящее принято), `assistant.answered`, `assistant.feedback`.
> * **Файловая шара** и **опубликованные API смежных сервисов** — источники справочного контента для индексации.
>
> **Как данные появляются в базе знаний:** планировщик или событие об изменении → чтение документа с шары или из API → проверка хэша (не изменился — пропуск) → извлечение текста → нарезка на чанки 300–800 токенов с перекрытием → эмбеддинги через провайдера → запись в векторную БД и реестр в PostgreSQL → снапшот исходника в S3 → старые чанки документа помечаются неактивными. Переиндексация атомарна: пока новая версия не готова, поиск идёт по старой.
>
> **Как идёт поиск:** вопрос → эмбеддинг → top-K по векторной БД с фильтрами → при необходимости гибрид с полнотекстом и реранжирование → контекст в промпт → ответ LLM со ссылками на источники. Нет релевантных чанков — честное «не знаю» и эскалация человеку.
>
> **Про данные других доменных сервисов:** **в момент вопроса живые API не вызываются.** В индекс попадает только справочный контент, полученный из опубликованных API смежных сервисов (услуги, тарифы, условия), и только он участвует в поиске. Бизнес-данные доменов (журнал сообщений, согласия, история клиента) не индексируются и помощнику недоступны — это другой контур и другие права. Точечный вызов API возможен только как отдельный сценарий-инструмент (например, «статус моей заявки») с авторизацией клиента, и это уже не RAG.
>
> **Чего не делает:** не отправляет сообщения сам (только через `delivery-service`), не меняет бизнес-данные, не хранит контент уведомлений, не ищет по живым API доменов.

**Внешние системы**

| Элемент | Бизнес-функция |
|---|---|
| SMS-провайдер, E-mail, Push (FCM/APNs), Telegram, MAX | Физическая доставка сообщения до человека |
| «Колокольчик» | Доставка внутрь интерфейса системы-потребителя (провайдера нет) |
| LLM | Отвечает на вопросы клиента в помощнике |
| Файловая шара | Источник справочной информации для помощника |

**Хранилища и шины**

| Элемент | Бизнес-функция |
|---|---|
| PostgreSQL | Источник правды: сообщения, шаблоны, согласия, задания |
| Redis | Ускорение и таймеры: кэш настроек, счётчики, ключи идемпотентности, отложенные отправки |
| S3/MinIO | Файлы и контент: вложения, отрендеренные письма, архив, снапшоты знаний |
| OpenSearch | Поиск по журналу и аудиту |
| Kafka | Гарантия, что принятое сообщение не потеряется: события и асинхронная обработка |
| RabbitMQ | Очереди отправки по каналам: приоритеты, повторы, «тяжёлые» сообщения |
| Векторная БД | Поиск по смыслу в базе знаний помощника |

# 1. Точечная отправка одному получателю или группе
*(кейсы 1–11, 14–18, 36)*

1. **Конвейер расчёта / ИТ-система** — формирует запрос: получатель, каналы, шаблон, данные, вложения. Бизнес-смысл: «сообщить клиенту о событии».
2. **API Gateway** — проверяет, что пришла доверенная система, не исчерпана ли её квота, и направляет в Notification API.
3. **Notification API** — валидирует запрос: существует ли шаблон, включён ли канал, есть ли согласие, готовы ли файлы. Ничего не создаёт, пока все проверки не пройдены.
4. **content-service** — проверяет шаблон и его версию, отдаёт его для рендера (из кэша, чтобы не тормозить).
5. **audience-service** — если указана группа, разворачивает её в контакты; проверяет по каждому согласие, opt-out, частотный лимит.
6. **delivery-service (приём)** — фиксирует сообщение и доставки в PostgreSQL одной транзакцией, ставит событие в outbox, отвечает потребителю «принято».
7. **Kafka** — переносит событие «сообщение принято» в асинхронную обработку; за счёт этого потребитель не ждёт отправки.
8. **delivery-service (обработка)** — берёт сообщение из очереди, блокирует его от повторной обработки, переводит в состояние «рендерится».
9. **content-service (рендер)** — подставляет данные клиента в шаблон, собирает текст/HTML, QR, ссылки; кладёт результат в S3.
10. **config-service** — по каналу определяет, какой провайдер доступен и какие у него лимиты.
11. **delivery-service (отправка)** — выбирает провайдера, проверяет его доступность, ставит команду в очередь канала.
12. **RabbitMQ** — очередь конкретного канала с приоритетом: транзакционные сообщения впереди массовых.
13. **Провайдер** — (SMS / e-mail / push / Telegram / MAX / «колокольчик») доставляет сообщение; возвращает свой идентификатор.
14. **Получатель** — клиент читает сообщение в своём канале.
15. **journal-service** — фиксирует факт отправки и, когда придёт квитанция, факт доставки; по этим данным строится история и отчётность.

# 2. Отложенная отправка
*(кейсы 12, 13)*

1. **Конвейер / система** — просит отправить не сейчас, а в конкретное время.
2. **API Gateway → Notification API → content + audience** — те же проверки, что и в потоке 1.
3. **delivery-service** — вместо немедленной отправки регистрирует задание с датой в PostgreSQL и Redis (список будущих отправок). Бизнес-смысл: «напомнить за 3 дня до окончания полиса».
4. **delivery-service (планировщик)** — по таймеру проверяет, какие задания наступили, и запускает обычный путь отправки. Если время попадает в ночь — переносит на разрешённое окно.
5. **Провайдер → получатель → journal-service** — как в потоке 1.
6. **Отмена** — администратор или система отменяет задание до наступления срока: запись снимается из PostgreSQL и Redis, отправки не будет.

---

# 3. Массовая рассылка
*(кейсы 19–27)*

1. **Back-office** — маркетолог создаёт кампанию: шаблон, каналы, расписание, аудитория (файл или сегмент).
2. **API Gateway → Notification API (batch-деплоймент)** — приём отдельного, более тяжёлого запроса; отдельная квота, чтобы рассылка не заблокировала точечные уведомления.
3. **content-service + audience-service** — проверка шаблона и оценка аудитории: сколько получателей, сколько отсеется по согласиям.
4. **delivery-service (создание задания)** — фиксирует задание, режет аудиторию на части по 500–1000 человек. Бизнес-смысл: рассылку можно ставить на паузу и не «ронять» провайдера.
5. **Kafka** — части задания уходят в отдельную очередь; их разбирает отдельный пул обработчиков, не конкурирующий с точечной отправкой.
6. **content-service (рендер)** — шаблон загружается один раз на часть, персонализация — на каждого получателя.
7. **RabbitMQ** — команды уходят с низким приоритетом; адаптер соблюдает технический лимит провайдера, чтобы тот не отклонил поток.
8. **Провайдер → получатели** — доставка на весь список.
9. **journal-service** — статусы по каждому получателю + агрегаты: сколько отправлено, доставлено, ошибок.
10. **Notification API (batch) → journal-service** — прогресс и ETA для админки; пауза/возобновление/отмена применяются на границе очередной части.

---

# 4. Лента «колокольчика»
*(кейсы 6, 44–46)*

1. **Потребитель** — отправляет уведомление по каналу «колокольчик» (внутри своей системы).
2. **Gateway → Notification API → delivery-service** — обычный путь приёма и доставки.
3. **delivery-service (плагин «колокольчик»)** — вместо внешнего провайдера событие уходит в шину: доставлять нужно внутрь интерфейса системы-потребителя.
4. **journal-service** — сохраняет элемент ленты для конкретного пользователя.
5. **Bell Inbox API** — отдаёт ленту по запросу и мгновенно пушит новые элементы в открытое приложение (WebSocket).
6. **Клиент** — видит счётчик и ленту в интерфейсе.
7. **Bell Inbox API → journal-service** — отметка «прочитано» сохраняется; счётчик непрочитанных уменьшается.

# 5. Статусы, история и подписки
*(кейсы 37–39, 43)*

1. **Система-потребитель** — спрашивает: «что с моим сообщением?».
2. **API Gateway → Query API** — проверка доступа и лимита на чтение.
3. **Query API → journal-service** — запрос статуса, истории за период, списка ошибок; поиск идёт по журналу и поисковому индексу.
4. **journal-service** — отдаёт данные: статус по каналам, попытки, коды ошибок провайдера.
5. **Подписка на события** — потребитель регистрирует адрес, куда сервис сам пришлёт уведомление о доставке; настройка хранится в config-service, отправляет события journal-service.

---

# 6. Квитанции и восстановление после сбоя
*(кейсы 40–42)*

1. **Провайдер** — присылает квитанцию: доставлено, прочитано, ошибка.
2. **API Gateway (/webhooks/v1/*)** — принимает внешний вызов, применяет защиту и лимиты.
3. **journal-service** — проверяет подпись, отбрасывает дубли, сохраняет квитанцию и публикует событие статуса.
4. **delivery-service** — если провайдер ответил ошибкой, повторяет отправку по расписанию (1 мин, 5 мин, 15 мин, 1 час, 6 часов). Бизнес-смысл: «сообщение не потерялось из-за временного сбоя».
5. **RabbitMQ** — хранит повторы и «мёртвую» очередь: после 5 попыток сообщение уходит в неё, а не теряется.
6. **journal-service** — фиксирует финальный статус «ошибка» с причиной.
7. **Notification API** — получает сигнал об инциденте и отправляет уведомление дежурным администраторам тем же сервисом (проверка, что система способна обслужить сама себя).

---

# 7. Управление контентом
*(кейсы 28–31)*

1. **Back-office** — контент-менеджер создаёт или правит шаблон.
2. **API Gateway → Admin API** — проверка прав администратора.
3. **content-service** — сохраняет черновик, ведёт версии, проверяет корректность переменных и условий.
4. **content-service (предпросмотр)** — рендерит шаблон на тестовых данных тем же движком, что и боевую отправку, чтобы админка не врала.
5. **S3/MinIO** — хранит изображения и файлы, на которые ссылается шаблон; проверка файла на вирусы идёт при загрузке.
6. **content-service (публикация)** — переводит версию в активную; новые сообщения используют новую версию, уже отправленные остаются на прежней.
7. **Кэши** — публикация сбрасывает кэш шаблона, чтобы в отправку не попал старый текст.

---

# 8. Управление настройками и согласиями
*(кейсы 32–35)*

1. **Back-office** — администратор меняет канал, лимиты, срок хранения или снимает согласие.
2. **API Gateway → Admin API** — проверка прав.
3. **config-service** — сохраняет настройку: включён ли канал, какая квота, сколько хранить сообщения; рассылает событие «настройки изменились», чтобы все сервисы обновили кэш.
4. **audience-service** — фиксирует отписку или согласие клиента; с этого момента он либо попадает, либо не попадает в рассылки.
5. **Влияние** — следующая отправка уже учитывает новые настройки и согласия: отписавшийся не получит сообщение, даже если он есть в списке.

# 9. Виртуальный помощник
*(кейсы 47–49)*

1. **Клиент** — пишет вопрос в Telegram или на e-mail.
2. **Мессенджер → API Gateway (/webhooks/v1/*)** — провайдер передаёт сообщение в систему; шлюз применяет защиту.
3. **assistant-service (приём)** — проверяет подлинность вызова, отбрасывает дубли, находит или создаёт диалог.
4. **assistant-service (поиск знаний)** — находит в базе знаний фрагменты, относящиеся к вопросу (поиск по смыслу в векторной БД).
5. **assistant-service (LLM)** — формирует ответ: промпт, найденный контекст, ограничения (не обещать того, чего нет в знаниях).
6. **delivery-service** — отправляет ответ клиенту тем же каналом, откуда пришёл вопрос.
7. **Провайдер → клиент** — клиент получает ответ.
8. **assistant-service** — сохраняет диалог; оценка ответа клиентом используется для контроля качества.

---

**Как читать схему одним предложением:** всё, что слева и сверху, — «кто просит»; API-слой — «принять и проверить»; домен — «сделать» (контент, аудитория, доставка, учёт); внизу — «через кого доставить»; справа — «где хранится правда».
