# Архитектура SuperSurance – Упражнение 5: Базовые платформенные сервисы

> Строится поверх схемы Упражнения 4.

## 1. Контекст

Платформенные сервисы не зависят от домена и бизнес-процесса, ими пользуются все. Они не должны знать ничего о заявках, тарифах и клиентах. У каждого своя БД, свой API и контракты событий, как и у доменных сервисов (Database per Service). Развивает их платформенная команда, доменные команды – потребители.

| Требование | Компонент | Статус |
|---|---|---|
| Роли и доступы | **IAM** (бывший Identity Provider) | расширяется |
| Генерация и хранение документов | **Document Service** + Document DB + Object Storage | новый |
| Централизованная НСИ | **Reference Data Service (НСИ)** + Reference DB | новый |
| Оркестрация и управление потоком событий | **Workflow Orchestrator**, **Schema Registry**, **Retry / DLQ**, каталог событий | новые |
| Уведомления (SMS, e-mail) | **Notification Service** (расширяется) + **Channel Gateway** | расширяется / новый |
| Иные решения | **Audit Service**, Observability, Secrets & Config, защита данных | новые |

## 2. IAM: роли и доступы

Identity Provider из Упражнения 1-4 (SSO, роли) превращается в полноценный IAM (решение класса Keycloak, OIDC / OAuth2) с собственной **IAM DB**.

**Кто аутентифицируется**
- Сотрудники (администраторы, андеррайтеры и др.): SSO, как раньше.
- Партнёры: OAuth2 client credentials, у каждого партнёра свой клиент и claim `partner_id`.
- Каналы «сайт» и «мобильное приложение»: клиенты каналов (client_id). Вход самого страхователя в личный кабинет вне объёма; IAM допускает отдельный realm под него позже.
- Сервисы между собой: OAuth2 client credentials, токены живут около 5 минут, у каждого сервиса свой набор scope. Дополнительно mTLS в сети.

**Модель доступа: RBAC + атрибуты**
- Роль = набор разрешений вида `ресурс:действие` (`proposal:read`, `underwriting:decide`, `product:write`, `reference:write`, `document:read`, `audit:read`, `pii:read`).
- Атрибутные ограничения: `partner_id` – партнёр видит только свои заявки и документы.
- Назначать роли может только `iam_admin`. Это разделение обязанностей: администратор продуктов не выдаёт права сам себе.

| Роль | Списки и карточка заявок | Задачи андеррайтинга | Продукты, тарифы | НСИ | Документы | Аудит | IAM |
|---|---|---|---|---|---|---|---|
| `admin` | чтение | просмотр | запись | чтение | чтение | – | – |
| `underwriter` | чтение (в т.ч. ПДн) | claim, решение | чтение | чтение | чтение по своим задачам | – | – |
| `ref_manager` | – | – | чтение | запись | – | – | – |
| `auditor` | – | – | – | – | – | чтение | – |
| `iam_admin` | – | – | – | – | – | – | запись |
| партнёр (client) | только свои | – | – | чтение | только свои | – | – |

**Проверяется доступ на двух уровнях**
1. Gateway и Internal Gateway проверяют подпись JWT (ключи JWKS кэшируются), срок действия и грубые права на маршрут.
2. Каждый сервис сам проверяет разрешения из claims. Gateway не может быть единственной защитой, иначе обход gateway открывает всё.

Токены короткоживущие (около 10 минут) + refresh с ротацией; отзыв доступа вступает в силу в пределах TTL.

**ПДн.** Полные ФИО и дата рождения клиента доступны ролям с `pii:read`; остальным Query Service и карточки отдают маскированные значения. Это закрывает пункт, оставленный в Упражнении 4.

## 3. Document Service: документы по заказам

**Типы документов**
- `OFFER` - предложение клиенту с расчётом премии;
- `CALCULATION_PROTOCOL` - протокол расчёта (входные данные, версия тарифа, коэффициенты) для споров и аудита;
- `UNDERWRITING_DECISION` - заключение андеррайтера (внутренний).

Новые типы добавляются шаблоном, без доработки кода.

**Устройство**
- **Document DB** – метаданные: `document_id`, `proposal_id`, `proposal_version`, тип, версия шаблона, `sha256`, ключ в хранилище, статус, срок хранения; шаблоны (версионируются, версия применяется только к новым документам); **снимок данных**, из которых документ построен.
- **Object Storage (S3-совместимое)** – сами PDF. Шифрование на стороне хранилища (KMS), режим неизменяемости (object lock): готовый документ не перезаписывается, при пересчёте создаётся новая версия, старая помечается `VOID`.

**Генерация асинхронная и идемпотентная.** Команда `GenerateDocument` приходит из брокера, ключ идемпотентности – `proposal_id + proposal_version + тип`. Результат – события `DocumentGenerated` или `DocumentGenerationFailed`.

**Откуда данные для шаблона.** Document Service запрашивает у Proposal Service представление `GET /proposals/{id}/document-data`. Proposal уже имеет связи с Customer и Product (данные клиента и тарифы для расчёта), поэтому не нужно, чтобы Document Service ходил в три сервиса и знал их модели. Полученный снимок сохраняется вместе с документом.

**Выдача**
- Back-office и каналы получают документ через gateway: проверка прав → короткая pre-signed ссылка (TTL около 5 минут); файлы идут напрямую из хранилища, а не через gateway.
- Клиенту в уведомлении уходит подписанная ссылка на скачивание (TTL около 72 часов, можно перевыпустить). ПДн в самой ссылке нет.
- Срок хранения определяется требованиями юристов и регулятора; в схеме параметр `retention_until`.

## 4. НСИ (Reference Data Service)

**Что в НСИ:** общие справочники, не принадлежащие одному домену: марки / модели / типы кузова ТС, регионы, причины передачи в андеррайтинг и отказа, типы документов, каналы подачи заявки, валюты.

**Чего в НСИ нет:** продукты и тарифы. Это бизнес-данные домена Product со своим жизненным циклом и версионированием (`tariff_versions`). Статусы заявок и задач тоже остаются в своих сервисах.

**Модель:** `dictionary` → `item` (код, наименование, атрибуты, родитель, `valid_from` / `valid_to`, статус `DRAFT` / `ACTIVE` / `ARCHIVED`). У каждого справочника монотонная `dictionary_version`, история не удаляется. Изменения проходят цикл «черновик → согласование второй стороной → активация» (роль `ref_manager`). Загрузка пакетом – через импорт CSV в back-office.

**Чтение**
- `GET /ref/{dictionary}?as_of=2026-10-03&version=...`, поддержка ETag.
- Сервисы-потребители используют клиентскую библиотеку с локальным кэшем. Кэш инвалидируется событием `ReferenceDataChanged` (TTL – страховка). Если НСИ недоступна, сервис работает на последнем кэше (stale-if-error). Горячий путь расчёта не зависит от синхронного вызова НСИ.
- Другие сервисы хранят у себя только **коды** (`make_code`). Расшифровки берут из НСИ. Витрина Query Service хранит названия как снимок из события заявки, как и раньше.
- Для форм сайта и мобильного приложения справочники отдаются через API Gateway.

**Связь с интеграциями.** Integration Service хранит соответствие кодов партнёров кодам НСИ (часть ACL из Упражнения 1): «LADA» и «ВАЗ» у разных партнёров приводятся к одному коду.

## 5. Оркестрация и управление потоком событий

### 5.1. Workflow Orchestrator

Движок процессов (класс Camunda / Temporal) + **Workflow DB** с состоянием экземпляров.

**Правило выбора.** По умолчанию остаётся хореография: простые реакции (наполнение витрины, уведомление о новой задаче) не требуют координатора. Оркестрация вводится только там, где процесс длиннее двух шагов, есть таймеры и повторы, и нужна видимость «на каком шаге завис». Центральный «супервизор всего» не строим.

**Процесс «Выпуск предложения»**

1. Старт по `ProposalChanged` со статусом «премия определена» (`CALCULATED`: автоматически или после `UnderwritingCompleted`). Идентификатор процесса – `proposal_id + version`, повторное событие не запускает второй экземпляр.
2. Команда `GenerateDocument` (OFFER и CALCULATION_PROTOCOL) → ожидание `DocumentGenerated`; таймаут 5 минут, 3 повтора с нарастающей паузой.
3. Команда `SendNotification` (шаблон `OFFER_READY`, получатель – клиент, ссылка на документ) → ожидание `NotificationSent`.
4. Публикуется `OfferIssued`.
5. Ошибка после повторов → `OfferIssuanceFailed` → Notification шлёт push администратору (механизм «ошибки» из Упражнения 3); в back-office доступен ручной повтор процесса.

**Компенсации.** Необратимых шагов (платежей) нет, поэтому компенсация простая: если заявка пересчитана (новая версия) пока процесс шёл, экземпляр отменяется, документ прежней версии получает `VOID`.

### 5.2. Управление потоком событий

- **Schema Registry.** Хранит схемы всех событий и команд (Avro / Protobuf / JSON Schema) и проверяет совместимость (BACKWARD): нельзя удалить обязательное поле, на которое рассчитывает потребитель. Каждый производитель сверяет сообщение со схемой при публикации, каждый потребитель читает по ней; проверка также стоит в CI производителя. На схеме показана одна связь с брокером, но фактически registry используют все сервисы, публикующие и читающие события. Единый конверт: `event_id`, `event_type`, `occurred_at`, `producer`, `schema_version`, `correlation_id`, `causation_id`. Это закрепляет идемпотентность и порядок из Упражнения 4.
- **Retry / DLQ.** Потребитель делает ограниченное число повторов с нарастающей паузой (retry-топики), затем сообщение уходит в DLQ, не блокируя партицию. Размер DLQ – алерт; из back-office (роль `ops`) возможен replay.
- **Каталог событий (AsyncAPI).** Не работающий сервис, а документация для людей и CI: владельцы топиков, потребители, версии, классификация ПДн, ACL. Генерируется из Schema Registry, поэтому во время работы системы запросов к нему нет. Именование топиков: `<домен>.<сущность>.<событие>.v1`.
- **Доступ к топикам** настраивается через сервисные клиенты IAM (ACL фиксируются в каталоге). Топик с контактами клиентов доступен только Notification Service.
- **Перестроение витрины.** Топик `ProposalChanged` с ключом `proposal_id` настраивается как compacted: Read DB Упражнения 4 можно полностью восстановить повторным проигрыванием.
- **Мониторинг** (в составе Observability): consumer lag, возраст необработанных записей outbox, размер DLQ.

## 6. Уведомления и коммуникации

### 6.1. Notification Service (расширение)

Каналы: WebSocket-push (сотрудники, как в Упражнении 3), **e-mail**, **SMS**; push в мобильное приложение можно добавить как ещё один адаптер.

- Источники: доменные события (как раньше) и команда `SendNotification` от оркестратора.
- **Шаблоны:** `template_code` + канал + локаль + версия. Короткие тексты без юридической силы (в отличие от документов).
- **Получатели-клиенты:** контакты и согласия хранятся репликой в Notification DB. Её наполняет новое событие `ClientContactsChanged` от Customer. Отдельное событие, а не поля `ClientUpdated`: Query Service не подписан на него, поэтому в витрине контактов нет.
- **Получатели-сотрудники:** по пользователю или роли из IAM (кэш).
- **Надёжность:** дедупликация по `command_id` / `event_id` + получатель + канал, повторы с паузой, ограничение частоты на получателя, fallback канала (e-mail → SMS). История отправок.
- Сейчас только служебные (транзакционные) сообщения. Маркетинговые рассылки требуют согласий и отписки и вне объёма.
- В Notification DB добавляется **outbox**: сервис публикует `NotificationSent` / `NotificationDeliveryFailed`.

### 6.2. Channel Gateway

Изолирует провайдеров так же, как Integration Service изолирует платных партнёров: единый внутренний контракт `send(channel, to, content, idempotency_key)`, по 2 провайдера на канал с переключением (circuit breaker), приём статусов доставки (webhook провайдера → `SENT / DELIVERED / FAILED` → Notification). Ключи провайдеров в Vault. Смена провайдера не затрагивает Notification.

## 7. Иные платформенные решения

- **Audit Service.** Сквозной неизменяемый (append-only) журнал: кто, что, над каким объектом, когда, с какого адреса, результат, `correlation_id`. Источники: доменные события (смена статусов, решение андеррайтера, изменения продуктов), события IAM (входы, смена ролей), Internal Gateway (просмотр ПДн, выгрузки, скачивание документов), изменения НСИ и шаблонов. Доступ – только роль `auditor`. Журнал задач в Underwriting Service (Упражнение 3) остаётся как бизнес-история процесса, это другая цель.
- **Observability.** OpenTelemetry: сквозной `correlation_id` проходит gateway → сервисы → события. Структурные логи без ПДн, метрики, трейсы, дашборды. Алерты: время расчёта, lag витрины, доля ошибок партнёров, DLQ, возраст outbox. Алерты уходят в Notification (канал `ops`).
- **Secrets & Config.** Vault для ключей партнёров и провайдеров, учётных данных БД (динамические, с ротацией), централизованная конфигурация.
- **Защита данных.** TLS и mTLS между сервисами, шифрование ПДн и документов at-rest (KMS), маскирование ПДн в логах и тестовых средах, процедура удаления / обезличивания по требованию субъекта в рамках законодательства о ПДн.

## 9. Изменения на схеме относительно Упражнения 4

**Изменены (зелёная рамка)**
- **IAM** (бывший Identity Provider) + новая **IAM DB**; связи gateway → IAM (JWKS, ключи партнёров), Internal Gateway → IAM (роли и права).
- **API Gateway** и **Internal Gateway**: проверка токенов через IAM, новые маршруты к Document Service и НСИ, аудит действий.
- **Notification Service** + Notification DB (outbox): шаблоны, каналы, статусы доставки; связь с Channel Gateway.
- **Customer Service**: событие `ClientContactsChanged`.
- **Proposal Service**: представление `document-data`, поле `version` в `ProposalChanged`.

**Новые (светло-зелёная заливка)**
- Группа «Оркестрация и управление событиями»: Workflow Orchestrator + Workflow DB, Schema Registry, Retry / DLQ, каталог событий (документация, генерируется из Schema Registry; пунктирная рамка).
- Группа «Документы»: Document Service, Document DB, Object Storage.
- Группа «НСИ · аудит · каналы связи»: Reference Data Service + Reference DB, Audit Service + Audit DB, Channel Gateway, внешние SMS- и e-mail-провайдеры.
- Группа «Сквозные платформенные средства»: Observability, Secrets & Config, защита данных.

Блоки Упражнения 4 (Query Service, Read DB, Integration Service) оформлены как существующие. Нижний блок интеграций и Read side сдвинут вниз, чтобы платформенные сервисы были рядом с брокером.

**Связи, не вынесенные на схему (чтобы не перегружать)**
- Все сервисы локально проверяют JWT по ключам IAM и получают сервисные токены у IAM.
- Notification получает сотрудников-получателей из IAM (кэш).
- Internal Gateway и IAM публикуют аудит-события в брокер.
- Все производители и потребители событий проверяют схемы через Schema Registry (на схеме одна связь с брокером).
- Все сервисы отправляют телеметрию в Observability и читают секреты из Vault.
- Потребители НСИ читают справочники по REST через клиентскую библиотеку с кэшем.
- Ручной повтор процесса из back-office через Internal Gateway к Orchestrator.

## 10. Почему не другие варианты

| Вариант | Почему нет |
|---|---|
| Роли и проверки доступа в каждом сервисе | Дублирование, расхождение прав, нет единой точки отзыва и аудита |
| Проверка прав только на gateway | Обход gateway открывает все сервисы; нужна проверка и в сервисах |
| Генерация документов внутри Proposal | Раздувает домен, шаблоны не версионируются отдельно, файлы лежат в БД сервиса |
| Хранить PDF как BLOB в БД | Рост БД, нет object lock и шифрования хранилища, тяжёлая выдача |
| Справочники отдельно в каждом сервисе | Рассинхронизация, разные коды |
| Общая БД справочников с прямым чтением | Ломает Database per Service (Упражнение 2) |
| Справочники внутри Product | Смешивает домены: марки ТС и регионы не относятся к продуктам |
| Выпуск предложения только хореографией | Таймеры, повторы и «где завис» размазаны по сервисам, нет единой точки управления |
| Оркестрировать всё | Центральный бог-сервис, связность между доменами |
| Прямые вызовы SMS / e-mail провайдера из Notification | Привязка к вендору, нет переключения при сбое |
| Отправка уведомлений из каждого сервиса | Дублирование шаблонов, предпочтений и ограничений частоты |

## 11. Допущения

- Конкретные продукты (Keycloak, Camunda, Vault, S3 и др.) названы как примеры класса решений, стек не фиксируем.
- Статус «премия определена» (`CALCULATED`) – условное имя; в реальной модели статусов Proposal это состояние после автоматического расчёта и после `UnderwritingCompleted`.
- Proposal собирает данные документа из своего хранилища деталей расчёта и уже существующих связей с Customer и Product.
- Аутентификация самого страхователя (личный кабинет) вне объёма.
- Сроки (TTL токенов и ссылок, таймауты процесса, retention документов) ориентировочные, согласуются с безопасностью и юристами.
